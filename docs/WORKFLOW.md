# 開発ワークフロー手順書

このドキュメントは、要件定義から実装・テスト・リリースまでを Claude Code と
一緒に進めるための手順書です。各フェーズには「成果物」と「完了条件」があり、
それを満たすまで次に進みません。

順番に読みながら実際に手を動かすことを想定しています。

---

## 全体像

| # | フェーズ | 成果物 | 目安 |
|---|---------|--------|------|
| 0 | 環境とルールの整備 | リポジトリ、CLAUDE.md、CI | 半日 |
| 1 | 要件定義 | docs/requirements.md | 半日 |
| 2 | 設計 | docs/design.md、docs/adr/ | 半日 |
| 3 | タスク分解 | docs/tasks.md | 1時間 |
| 4 | 実装（反復） | コードとテスト | タスク数 × 半日 |
| 5 | レビュー | レビュー指摘の反映 | タスクごと |
| 6 | 結合確認 | 動くアプリ | 1日 |
| 7 | リリースと振り返り | 公開URL、振り返りメモ | 半日 |

原則: **フェーズ1〜3でコードは1行も書きません。** ここを飛ばして実装に入ると、
作り直しが発生します。急いでいるときほど守る価値があります。

---

## ブランチの粒度

フェーズによって基準が違います。**同じ基準を全フェーズに当てると破綻します。**

| 種類 | フェーズ | 粒度 | ブランチ名 |
|------|---------|------|-----------|
| 探索フェーズ | スパイク・要件定義・設計（0〜2） | **1フェーズ = 1ブランチ** | フェーズを表す名前（例 `spike/route-feasibility`、`docs/requirements-and-design`） |
| 実装フェーズ | 実装以降（3〜7） | **1タスク = 1ブランチ、半日以内** | タスクを表す名前（例 `feat/ors-client`） |

**探索フェーズを事前に分割しないのは、次にやることが結果次第で変わるからです。**
スパイクを走らせるまで、何が分かるか（したがって次に何を書くか）が決まりません。
着手時点でタスクに切れないものを無理に切ると、実態と合わない管理が残ります。

### この規約を改訂した理由（2026-08-05）

当初は全フェーズに「1タスク = 1ブランチ = 1PR、半日以内」を当てていました
（**当時の規約をそのまま引用しています。** PR を必須にする部分は 2026-08-06 に
撤回しました。フェーズ5 の完了条件を参照）。
探索フェーズでは成立しませんでした。実例を残します。

- ORS 検証スパイク4本（計 127 呼び出し）の結果で2段方式の採否が決まった
- その結果が要件定義の改訂内容（版1.1）と設計書の中身を決めた
- さらに設計書を書く過程で生データを読み直し、スパイクの記録の誤りが3件見つかり、
  要件定義をもう一度改訂した（版1.2）
- **着手時点では、ADR を4件書くことも要件定義を2回改訂することも分からなかった**
- 結果として1本のブランチに要件定義・設計・ADR・訂正が乗った

**規約が現実と噛み合わなかったので、規約側を直しました。**
探索の成果物が事前に読めないことは避けられる失敗ではなく、探索の性質です。

## フェーズ0: 環境とルールの整備

### やること

```bash
# プロジェクト作成
mkdir run-loop && cd run-loop
uv init --python='>=3.10'
uv venv
.venv\Scripts\activate          # Windows
git init

# 開発ツールを入れる
uv add streamlit requests folium python-dotenv
uv add --dev pytest pytest-cov responses ruff mypy pre-commit

# 秘密情報を守る
echo ".env" >> .gitignore
echo ".venv/" >> .gitignore
echo "__pycache__/" >> .gitignore
```

`.env.example` を作ってコミットします（キーの値は空にする）。
これがあると、他の人が何を設定すべきか分かります。

```
ORS_API_KEY=
HOME_LAT=
HOME_LON=
```

### Claude Code の初期設定

```bash
claude
```

セッション内で順番に実行します。

| コマンド | 目的 |
|---------|------|
| `/init` | CLAUDE.md のひな形を自動生成 |
| `/memory` | 生成された内容を自分の言葉で調整 |
| `/permissions` | どのコマンドを自動承認するか決める |

`/permissions` では `uv run pytest` や `uv run ruff` のような
読み取り・検証系を許可しておくと、確認を求められる回数が激減します。
逆に `git push` や `rm` は毎回確認させたままにします。

### CLAUDE.md に書くこと、書かないこと

判断基準はひとつです。**「これを書かないと Claude が間違えるか？」**

書く:
- ツールのデフォルトと違う選択（「requests ではなく httpx を使う。理由は非同期対応」）
- ハマりどころ（「ORS が返す距離は目標値より長くなる傾向がある」）
- 守ってほしい規約（「型ヒントを必ず書く」「1ファイル300行以内」）
- 自分について（「Python は書けるがモバイル開発は初めて」）

書かない:
- ディレクトリ構成（コードを見れば分かる）
- 依存パッケージ一覧（pyproject.toml を見れば分かる）
- 一般的な Python の書き方

長い CLAUDE.md は指示が無視される確率を上げます。60行を超えたら、
本当に必要かを見直してください。

**60行という数字自体に根拠はありません。目安として置いたものです。**
上限の目的は「増える一方になっていないか点検すること」であり、
数字そのものを守ることではありません。超過したときにまず削るのではなく、
何が超過させたかを見てください。実際に外した点の蓄積（CLAUDE.md
「間違えやすい設計判断」のような節）が主因なら、削れば同じ間違いが戻るので、
上限側を見直す方が理にかないます。**元は50行でしたが、超過の主因がこの種の
節だったため、2026-08-05 に60行へ改訂しました。**
**ただし上限を撤廃はしません。** 長いと精度が落ちるという理由は今も有効です。

### 完了条件

- [ ] `git log` に初回コミットがある
- [ ] `.env` が git に含まれていない（`git status` で確認）
- [ ] `uv run pytest` がエラーなく終わる（テストがゼロでもよい）
- [ ] CLAUDE.md が60行以内

## フェーズ1: 要件定義

ここが一番大事で、一番飛ばされがちな工程です。

### コツ: Claude に「質問させる」

自分から要件を書き出すと、必ず抜けが出ます。
Claude をヒアリング役にすると、自分では気づかない穴が見つかります。

最初のプロンプト例:

```
これから作るアプリの要件定義をしたいです。
まだドキュメントは書かないでください。

やりたいことの概要:
鹿児島マラソンに向けた練習で、自宅を起点・終点として
指定した距離ちょうどに近い周回ランニングコースを提案する Web アプリ。

私が答えるべき質問を、優先度の高いものから5つずつ出してください。
曖昧な点、決めていない点を洗い出したいです。
```

質問に答えていき、出尽くしたら次に進みます。

### 成果物: docs/requirements.md

以下の6つの節を必ず含めます。

**1. 背景と目的**
なぜ作るのか。1〜3文。「既存アプリでは指定距離の周回コースが作れないため」など。

**2. ユーザーストーリー**
「〜として、〜したい。なぜなら〜だから」の形式で書きます。

```
US-01: ランナーとして、距離を指定して周回コースを見たい。
       なぜなら、走る前にコースを決めておきたいから。
US-02: ランナーとして、複数の候補から選びたい。
       なぜなら、同じコースばかりだと飽きるから。
```

**3. スコープ（重要）**
「やること」と同じ分量で「やらないこと」を書きます。
ここを書かないと、作業が無限に膨らみます。

```
やること:
- 距離を指定して周回ルートを生成する
- 候補を地図上に表示する

やらないこと（今回は）:
- 走行中の GPS 計測（既存アプリに任せる）
- ユーザー登録・ログイン
- 複数の自宅地点の登録
- 練習計画の自動生成
```

**4. 受け入基準**
各ユーザーストーリーに対し、テストに変換できる粒度で書きます。
「使いやすいこと」はダメ。「〜すると〜になる」の形にします。

```
US-01 の受け入基準:
- 5.0 km を指定すると、実距離が 4.7〜5.3 km の範囲のルートが1件以上返る
- ルートの始点と終点が自宅座標から 50 m 以内である
- API が失敗した場合、エラーメッセージが画面に表示される
```

この節がフェーズ4のテストコードに直結します。曖昧に書くと後で困ります。

**5. 非機能要件**
性能、可用性、制約など。

```
- ルート生成は10秒以内に完了する
- ORS の無料枠（1日あたりの上限）を超えない
- API キーはソースコードに含めない
```

**6. 用語定義**
「周回ルート」「候補」「シード」など、この先ずっと使う言葉の定義。
チーム開発では特に効きます。

### 完了条件

- [ ] 「やらないこと」が3つ以上書かれている
- [ ] すべての受け入基準が数値または真偽で判定できる
- [ ] docs/requirements.md がコミットされている

## フェーズ2: 設計

### プランモードを使う

<Shift+Tab> または `/plan` でプランモードに入ります。
プランモードは計画を立てるだけで、ファイルを書き換えません。

```
/plan

docs/requirements.md を読んで、実装の設計をしてください。
以下を含めてください。

- モジュール構成（何をどのファイルに置くか、その理由）
- データ構造（周回ルート候補をどう表現するか）
- 外部API（ORS）の呼び出しをどう抽象化するか
- API が失敗したときの挙動
- テストしやすくするための工夫

コードは書かないでください。設計の議論だけしたいです。
```

計画に納得できないときは、遠慮なく指摘してください。
「この分割だと距離計算のテストが書きにくいのでは？」のような
問いを投げると、設計が締まります。**ここに時間をかけると実装が速くなります。**

### 成果物: docs/design.md

- モジュール構成と責務
- 主要なデータ構造
- 外部APIの抽象化方針
- エラー処理の方針
- テスト戦略（何を単体テストし、何をモックするか）

### 成果物: docs/adr/

ADR（Architecture Decision Record）は「なぜその技術を選んだか」の記録です。
1決定 = 1ファイル。半年後の自分と、引き継ぐ人のために書きます。

`docs/adr/0001-use-openrouteservice.md`

```markdown
# 0001: 周回ルート探索に OpenRouteService を使う

## ステータス
採用（2026-08-04）

## 背景
指定距離の周回ルートを生成する必要がある。

## 検討した選択肢
1. OpenRouteService — round_trip オプションあり、無料枠が比較的大きい
2. GraphHopper — round_trip アルゴリズムあり、無料枠は小さめ
3. 自前実装（OSM データ + 探索アルゴリズム） — 工数が大きすぎる

## 決定
OpenRouteService を採用する。

## 理由
- round_trip が公式機能として存在する
- 無料枠で個人利用に足りる
- 階段回避（avoid_features）が指定できる

## 結果として受け入れるリスク
- 返却距離が目標値からズレる（補正係数で対応する）
- サービス停止時に代替手段がない（将来 GraphHopper に切替可能な設計にする）
```

ADR を書く習慣は、実務で最も評価される部分のひとつです。

### 完了条件

- [ ] docs/design.md に「何をモックするか」が書かれている
- [ ] ADR が1件以上ある
- [ ] 設計を読んで、自分がその通りに実装できると思える

## フェーズ3: タスク分解

### 粒度の基準（ここからは実装フェーズの基準です）

- 1タスク = 1 ブランチ
- 1タスクは**半日以内**に終わる大きさ
- 1タスク完了時に「動く何か」が増えている

大きすぎるタスクは、レビューが不可能になり、失敗しても原因が分かりません。

**この基準はフェーズ3以降にだけ当てます。** フェーズ0〜2（スパイク・要件定義・設計）は
1フェーズ = 1ブランチで、事前にタスクを切りません（「ブランチの粒度」）。
フェーズ3 でタスクに割れるようになるのは、**設計が終わって初めて
「次に何をやるか」が確定するから**です。

### プロンプト例

```
docs/requirements.md と docs/design.md をもとに、
実装タスクに分解してください。

条件:
- 1タスクは半日以内で終わる粒度
- 依存関係の順に並べる
- 各タスクに「完了条件」を受け入基準から引用して書く
- まだファイルに書かず、一覧を提示するだけにしてください
```

一覧を確認して納得したら、`docs/tasks.md` への書き出しを依頼します。
**状態はこのファイルだけで管理します。** 一覧表にも状態を持たせると、
2か所に書くことになり必ず食い違います。

### タスク一覧の例

```
T01 CI（ruff + mypy + pytest）の設定
T02 ORS クライアントの実装（1件のルートを取得する）
T03 距離誤差による候補選択ロジック
T04 folium での地図描画
T05 Streamlit の入力フォームと結果表示
T06 エラー処理（API 失敗、候補ゼロ件）
```

### 完了条件

- [ ] すべてのタスクに完了条件が書かれている
- [ ] 依存順に並んでいる
- [ ] 半日を超えそうなタスクがない

## フェーズ4: 実装（1タスクずつ反復）

ここからは、以下のサイクルを1タスクごとに繰り返します。

### 1タスクのサイクル

```
/clear                              ← 前のタスクの文脈を捨てる
```

`/clear` は毎タスクの開始時に必ず実行します。
前のタスクの会話が残っていると、Claude が古い前提で動き、精度が落ちます。
CLAUDE.md は消えないので、プロジェクトの前提は保たれます。

```bash
git switch -c feat/ors-client
```

そしてプロンプト。**テストを先に書かせるのが要点です。**

```
docs/tasks.md の T01 に着手します。
docs/design.md の方針に沿って、以下の順で進めてください。

1. まずテストを書く。ORS の HTTP 通信は responses ライブラリでモックする
2. テストを実行して、失敗することを確認する
3. 実装してテストを通す
4. リファクタリング

各ステップが終わるたびに止まって、私に確認を求めてください。
```

「失敗することを確認する」を入れるのが大事です。
これを省くと、実は何もテストしていないテストが混入します。

### テスト方針

| 対象 | 方法 |
|------|------|
| 距離計算、候補選択などの純粋なロジック | 通常の単体テスト |
| 外部API（ORS）の呼び出し | `responses` でモック |
| 地図描画 | HTML に想定の座標が含まれるかを確認 |
| Streamlit の画面 | 手動確認（自動化は費用対効果が悪い） |

**外部APIを叩く自動テストは書きません。** 遅く、不安定で、
無料枠を消費するためです。代わりに ORS のレスポンスを1件だけ
実データで取得して `tests/fixtures/` に JSON として保存し、
それをモックの返り値に使います。これは実務でも標準的な手法です。

### コミット

テストが通ったらコミットします。**差分を自分の目で読んでから**です。

```bash
git add -A
git diff --cached          # 自分で読む
git commit -m "feat: ORS クライアントを追加"
```

Claude にコミットを任せることもできますが、学習目的なら
最初のうちは自分で差分を読む習慣をつけてください。
ここを飛ばすと「動いているが理解していないコード」が溜まります。

### 完了条件（各タスク）

- [ ] docs/tasks.md の完了条件を満たしている
- [ ] テストが通る
- [ ] `uv run ruff check` が通る
- [ ] 差分を自分で読んで理解している

## フェーズ5: レビュー

実装した本人（Claude 自身）にレビューさせても、見落としが同じになります。
Claude Code のレビュー機能は別コンテキストで動くので、これを使います。

```
/diff                    ← 変更内容を目で確認
/code-review             ← 正しさのバグと改善点をチェック
/security-review         ← セキュリティ観点のチェック
```

`/code-review` は `--fix` を付けると指摘を自動で適用できますが、
**学習目的では最初は付けないでください。** 指摘を読んで、
自分で直すか判断する練習の価値が大きいです。

秘密情報の扱いを変えたときは `/security-review` を必ず流します。
API キーの漏洩は、この規模のアプリでも実際に起こる事故です。

### 自分でも読む観点

- 受け入基準を本当に満たしているか（requirements.md と照合）
- エラー時の挙動が定義通りか
- テストが「実装をなぞっただけ」になっていないか
- 設計から逸脱していないか（逸脱したなら design.md を更新する）

### 完了条件

- [ ] `/code-review` の指摘に対応済み、または対応しない理由が説明できる
- [ ] `/security-review` で重大な指摘がない
- [ ] 変更が main に入った

**PR は必須にしません。** 1人開発でレビュワーがいないため、PR の本来の目的
（他人のレビューを受ける）が成立しません。差分をまとめて読み返したいときの手段として
使うのは有効ですが、使わずに main へ直接マージしてもフェーズ5は完了とします。

## フェーズ6: 結合確認とCI

### CI を入れる

`.github/workflows/ci.yml` で、push ごとに自動チェックさせます。

```yaml
name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v6
      - run: uv sync --all-extras --dev
      - run: uv run ruff check .
      - run: uv run pytest --cov
```

CI があると「自分の環境では動く」問題が減ります。
チーム開発では必須なので、個人開発でも練習として入れておく価値があります。

### 手動での結合確認

受け入基準を上から順に、実際の画面で確認します。
チェックリストにして潰していくのが確実です。

```
[ ] 5.0 km を指定 → 4.7〜5.3 km のルートが表示される
[ ] 始点と終点が自宅から 50 m 以内
[ ] API キーを空にする → エラーメッセージが表示される
[ ] 極端な値（0.1 km、100 km）→ 適切に扱われる
```

最後の「極端な値」は自分では思いつきにくいので、
Claude に「このアプリの異常系テストケースを10個挙げて」と
聞くと良い訓練になります。

## フェーズ7: リリースと振り返り

### デプロイ

Streamlit Community Cloud に GitHub リポジトリを繋ぐと無料で公開できます。
API キーは Streamlit の Secrets 機能で設定し、コードには含めません。

公開後、iPhone の Safari で開いて「ホーム画面に追加」すれば
アイコンから起動できます。

### 振り返り（これが学習の本体）

`docs/retrospective.md` に書きます。

- 想定より時間がかかった工程はどこか、なぜか
- 要件定義で漏れていたことは何か
- Claude Code の使い方で効いたこと、効かなかったこと
- 次のプロジェクトで変えること

この振り返りが、会社で Claude を展開するときの一次資料になります。

## Claude Code を使うときの規律まとめ

| 規律 | 理由 |
|------|------|
| タスクごとに `/clear` | 古い文脈が判断を狂わせる |
| 探索は1フェーズ1ブランチ、実装は1タスク1ブランチ | 探索は次にやることが結果次第で変わり、事前に分割できない |
| 設計はプランモードで、コードを書かせない | 手戻りを防ぐ |
| テストを先に、失敗を確認してから実装 | 空のテストを防ぐ |
| 差分を自分の目で読んでからコミット | 理解しないコードを溜めない |
| レビューは別コンテキストで | 同じ見落としを繰り返さない |
| `/context` で肥大を監視 | 長い会話は精度が落ちる |
| CLAUDE.md は60行以内（目安） | 長いと指示が無視される。数字自体より増加傾向の点検が目的 |

### よくある失敗

**「アプリを作って」と丸投げする**
数千行が一度に生成され、理解も修正もできなくなります。
タスクを半日単位に割るのは、Claude のためではなく自分のためです。

**動いたから良しとする**
テストがない、または実装をなぞっただけのテストしかない状態は、
次の変更で壊れます。受け入基準から逆算してテストを書きます。

**設計を飛ばす**
実装しながら設計すると、途中で構造の破綻に気づいて作り直しになります。
プランモードで30分議論するほうが、3時間の手戻りより安いです。
