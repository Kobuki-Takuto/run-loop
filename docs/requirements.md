# 要件定義書: 周回ランニングコース提案アプリ（仮称 RunLoop）

- 版: 1.1（確定）
- 作成日: 2026-08-04
- 最終更新: 2026-08-05
- ステータス: 確定。未決事項なし
- 版1.1の根拠: `spike/FINDINGS.md`（ORS 検証スパイク4本・API 呼び出し計 127 回の実測）

**版1.1の数値はすべて実測に紐づく。** 根拠の一覧は 10節。
実測がなく設計判断で決めた数値は、その旨を明記している。

## 1. 背景と目的

### 背景

鹿児島マラソン完走に向けて練習を積む必要がある。練習では「今日は5km」と
距離を決めて走るが、既存のランニングアプリには
「指定した距離ちょうどで出発地点に戻るコースを提案する」機能がない。

結果として、走りながら距離を調整することになり、家の前で
中途半端に足りない距離を往復する、あるいは走り過ぎるといった不便がある。

### 目的

出発地点を指定して距離を入力すると、その距離に近い周回コースを1本提案する
Web アプリを作る。走る前にコースを確認し、そのまま走り出せる状態にすることが目的。

### 目的の達成基準

走った結果として、実走距離が目標距離の ±50m に収まること。

ただしこれはアプリ単体で達成する数値ではない（4.1 参照）。
アプリはコースと差分の提示までを担い、最後の数百メートルの調整は
走行中に人が行う。アプリの品質基準は 5. の受け入基準に定める。

## 2. 用語定義

| 用語 | 定義 |
|------|------|
| 起点 | ユーザーが地図上でクリックした出発点かつ終点。通常は自宅。 |
| 目標距離 | ユーザーが入力する希望距離（km）。 |
| 候補 | API から取得した周回ルート1本。内部的に複数生成する。 |
| **ループ距離** | **API が返すルート本体の距離（m）。ルート始点から始点に戻るまで。** |
| **接近距離** | **起点と、API がルート始点として返した座標との直線距離（m）。** API は起点を最寄りの道路上に寄せる（スナップ）ため、両者は一致しない。 |
| **合計距離** | **ループ距離 + 接近距離 × 2（m）。ユーザーが実際に走る距離。判定と表示はこの値で行う（4.4）。** |
| 距離誤差 | 合計距離 − 目標距離。正なら長い、負なら短い。 |
| 獲得標高 | ループ区間での上り累計（m）。坂の多さの指標。接近区間は含まない（4.5）。 |
| シード | ルート生成の乱数の種。変えると別の形のコースが得られる。 |
| チェックポイント | 走行中に方向転換する主要地点。最大5か所を表示する。 |
| 在庫 | 1回の実行で得た候補のうち、合計距離が ±300m 以内のもの。引き直し（US-08）はここから出す。 |

版1.0の用語「実距離」は廃止し、「合計距離」に統一した（9節）。

## 3. スコープ

### 3.1 やること

- 地図をクリックして起点を指定する
- 指定した起点を1件保存し、次回起動時に自動で復元する
- 目標距離を入力する
- 周回コースの候補を内部で複数生成し、条件に従って1本を選ぶ
- 選んだコースを地図上に表示する
- 合計距離と距離誤差を表示する
- 距離が足りない場合、調整方法を案内する
- チェックポイントを最大5か所表示する
- 階段を通らないコースを生成する
- 候補の中から坂の少ないものを優先して選ぶ
- **同一セッション内での候補切り替え（引き直し。US-08）**

### 3.2 やらないこと（今回は実装しない）

以下は意図的に対象外とする。要望として存在するが、今回は作らない。

| 項目 | 理由 |
|------|------|
| 走行中の GPS 距離計測 | iPhone 標準のフィットネスアプリ等が既に十分な機能を持つ |
| 音声によるコース案内 | ブラウザでは画面消灯時に処理が止まるため技術的に不可能 |
| 走行履歴の保存 | データベースが必要になり工数が大きい |
| **セッションを超えた「前回と違うコース」の提示** | **履歴の保存が前提となる。同一セッション内の切り替えは US-08 で実装する（3.1）** |
| 現在位置の自動取得 | 起点を保存して復元するため不要。依存を増やさない判断 |
| 住所・建物名による起点検索 | 日本の住所に対するジオコーディング精度が不確実 |
| 信号の少ないコースの生成 | 利用予定の API に信号のデータが存在しない |
| 練習計画の自動生成 | 本アプリの中核価値ではない |
| ユーザー登録・ログイン | 個人利用のため不要 |
| 複数の起点の登録 | 自宅1か所で足りる |
| 接近区間の経路案内 | ルートに含まれないため、道も獲得標高も取得できない（4.5） |

### 3.3 将来やりたいこと

今回は作らないが、要望として記録しておく。

- 負荷の選択（坂の多いコース／少ないコースをユーザーが選ぶ）
- 音声によるコース案内（ネイティブアプリ化が前提）
- 信号の少ないコースの生成（別のデータ源が必要）
- 住所・建物名による起点検索
- 走行履歴と、それを使ったコースの重複回避（セッションを超えた重複回避）
- 練習計画の自動生成と、計画に応じたコース提案の連動

## 4. 前提と制約

### 4.1 精度の責任分担

目的の達成基準である ±50m は、以下の3段階で達成する。
アプリが担保するのは最初の2つのみ。

| 段階 | 担い手 | 精度 |
|------|--------|------|
| コースを生成する | アプリ | 合計距離で ±300m |
| 合計距離と差分を表示する | アプリ | 誤差なし（表示は正確）。ただし接近距離の直線近似ぶんだけ過小評価（4.4） |
| 走行中に不足分を調整する | 人 + 既存の計測アプリ | ±50m |

外部 API が返す距離は近似値であり、シードを変えて複数試しても
±50m に収まる保証はない。この制約を前提に設計する。

**±300m は「候補1本あたり」ではなく「複数投げた中から選べる」前提の数値である。**
候補1本が ±300m に入る確率（命中率）は実測 33.3%（n=30, 95%CI 19.2%〜51.2%）で、
1本では担保できない。15本投げることで担保する（7節）。

**接近距離が 50m を超える場合、この ±300m は保証の対象外とする**（AC-01-3）。
理由は 4.4。

### 4.2 技術的制約

- 開発環境は Windows。iOS 向けのネイティブアプリはビルドできない
- 成果物はブラウザで動作する Web アプリとする
- 外部 API は無料枠の範囲で利用する
- 使用する OpenStreetMap のデータには、日本の生活道路の名称が
  含まれていないことが多い。**実測では 86 step のうち 82 件（95%）で
  `name` が文字列 `"-"` だった**（FINDINGS スパイク1）。
  地点名は取得できる場合のみ表示する（AC-04-4）

### 4.3 利用状況の前提

走る直前に、自宅でスマートフォンから操作する。
屋外で走りながら操作することは想定しない。

### 4.4 合計距離の算出と、直線近似の向き

API は起点をそのまま使わず、最寄りの道路上に寄せた座標（スナップ先）から
ルートを開始する。したがってユーザーが実際に走る距離は次のようになる。

```
接近距離   = haversine(起点, API が返したルート始点)   ← 直線距離
合計距離   = ループ距離 + 接近距離 × 2
距離誤差   = 合計距離 − 目標距離
```

接近距離を2倍するのは、起点から道路まで出て、帰りに同じ区間を戻るため。
ルートの始点と終点の距離は実測 0.0m（完全な周回）なので、往路と復路は
同一区間とみなせる（FINDINGS スパイク3「AC-01-3」）。

**この算出は必ず過小評価方向に外れる。** 接近距離は直線距離であり、
実際には道に沿って移動するため「直線距離 ≤ 実際の移動距離」が常に成り立つ。
つまり表示される合計距離は真の走行距離を上回ることがなく、
**実走は表示より長くなる方向にしかずれない。**

実測ではこの過小評価は無視できる大きさだった。自宅座標での接近距離は
**0.7m（自宅での成功応答 99 回すべて同一値）**で、合計距離への寄与は 1.4m
（FINDINGS スパイク3 は n=39 と記載。本書作成時にスパイク4 の CSV でも 60 件すべて
0.7m を確認したため n=99 とした）。
また**スナップ先は起点座標だけで決まりシードに依存しない**ことが実測で確定しており、
接近距離は1回の実行の中で全候補に共通の定数として扱える。

ただし道路から離れた地点をクリックした場合は接近距離が大きくなり、
過小評価も比例して大きくなる。このため接近距離に3段の閾値を設ける（AC-01-3）。

**閾値 50m / 300m は実測値ではなく、誤差予算 ±300m からの逆算である。**
接近距離が d のとき、直線近似の過小評価量は「2d ×（迂回率 − 1）」に等しい。
迂回率は未実測だが、市街地では 1.3〜1.5 程度とされる。d=50m なら過小評価は
30〜50m 程度で誤差予算に収まる。d=300m なら 180〜300m となり、
**接近区間だけで ±300m の予算を単独で使い切りうる。** ゆえに 300m 超は拒否する。
迂回率の実測はスパイクで行っていない（10節の「実測なし」欄）。

### 4.5 接近区間はルートではない

接近区間（起点 ↔ スナップ先）は API が返すルートに含まれない。したがって、

- **接近区間の道は取得できない。**地図上に線を描けず、経路案内もできない
- **接近区間の獲得標高は取得できない。**表示する獲得標高はループ区間のみ（AC-03-3）
- 表示できるのは接近距離という1つの数値だけである

これは実装上の手抜きではなく、API のレスポンスにデータが存在しないことによる。
ユーザーには「起点から最寄りの道路までは自分で出る」ことを前提としてもらう。

### 4.6 呼び出しの失敗率と異常率（実測）

いずれも FINDINGS「設計に効いた発見」2 および各スパイクの実測。
括弧内は Wilson 法による 95% 信頼区間（本書で算出）。

| 事象 | 自宅座標 | 暫定座標（鹿児島市役所付近） |
|------|----------|------------------------------|
| 404（ルート生成不能） | 1/103 = 約 1.0%（0.2%〜5.3%） | 2/23 = 8.7%（2.4%〜26.8%） |
| 異常ルート（目標の3倍超） | 0/103 = 0%（0%〜3.6%） | 2/23 = 8.7%（2.4%〜26.8%） |
| 429（レート制限） | 直近1分に約 40 回投げた時点で発生 | 同じ |

読み取れること。

1. **失敗率と異常率は場所に依存する。** 暫定座標では約 415km・416km という
   異常ルートが2件出たが、自宅座標では 103 回で1件も出ていない。
   特定地域固有の現象の可能性がある（FINDINGS 同項）
2. **信頼区間は広い。** 自宅の 404 が 1/103 でも上限は 5.3% ある。
   「ほぼ起きない」とは言えるが「起きない」とは言えない。US-06 の異常系処理は必須
3. **異常ルートは必ず捨てる。** サニティ上限（目標の3倍超）を実装する（AC-01-5）
4. **429 は無料枠を消費しないが、404 は消費する。**
   FINDINGS スパイク3 副産物は「404 と 429 は消費しない」としているが、
   **これは誤りである**（下記 4.6.1）。ルートが見つからない起点でリトライを繰り返すと
   無料枠を減らす。加えて 429 は枠を消費しなくても毎分制限には触れるので、
   いずれにせよリトライは慎重に

### 4.6.1 無料枠の消費に関する FINDINGS の訂正

FINDINGS スパイク3「副産物」および「設計に効いた発見」4 は
「404 と 429 は無料枠を消費しない」としている。**404 については誤りである。**
本書作成時に `spike/out/*.csv` の `ratelimit_remaining` 列を再集計して確認した。

| スパイク | 呼び出し | 内訳 | 残数の推移 | 実際の消費 |
|---|---|---|---|---|
| スパイク2 | 23 回 | 200×21, 404×2 | 1997 → 1975 | **23**（全件） |
| スパイク3 | 43 回 | 200×39, 404×1, 429×3 | 1975 → 1935 | **40**（429 の3件のみ非消費） |
| スパイク4 | 60 回 | 200×60 | 1934 → 1875 | 60（全件） |

- CSV の各行を見ると、**404 の行でも残数は 1 減っている**（スパイク2 の 1992→1991 など）
- FINDINGS が「43 回で減少 39」としたのは、1本目の応答が返した残数（1974）を
  起点として数えたためで、**1本目自身の消費が抜けている**（off-by-one）。
  正しくは 1975 → 1935 の 40 消費で、これは 200 の 39 件 + 404 の 1 件に一致する
- 429 は残数ヘッダ自体が返らず、消費もされていない（43 − 40 = 3 = 429 の件数）
- 上表の合計（23 + 40 + 60 = 123）にスパイク1 の 1 回を足すと 124 だが、
  残数の実測は 2000 → 1875 の **125 消費**で、1 回ぶん出所が不明である。
  キー有効性の確認としてブラウザから1回叩いたもの（スクリプト外のため CSV に記録なし）
  と推定しているが**未確認**。上表のとおり各スパイクでは呼び出し数と消費数が
  一致しているため、1呼び出し1消費のモデル自体は成立している
  （FINDINGS「訂正（2026-08-05 追記）」の補足）

**設計への影響:** 404 が返る起点に対する自動リトライは無料枠を消費する。
無料枠 2000 回/日に対する影響は小さいが、「失敗はタダ」という前提での
リトライ設計はしない。生データは `.gitignore` 済みで repo に無いため、
上の残数の数値を本書に転記して残す。

### 4.7 実測の適用範囲と限界

版1.1 の数値をそのまま信じてよい範囲を明示する（FINDINGS「測定の限界」）。

- **起点は2点のみ**（自宅1点、暫定1点）。他の場所での命中率・失敗率は不明
- **目標距離は 5km のみ。** 3km / 10km で距離比の分布が同じかは未検証。
  距離依存があれば命中率の数字はそのまま使えない
- **n=30 でも信頼区間は ±16pt 程度。** 決定ルールの判定には足りたが、
  細かい最適化の根拠には使えない
- `points=3` 中心。`points=2` は未検証。`foot-walking` のみ
- 起点の永続化方式（ブラウザ側）はスパイク未実施。US-07 は未実測の要件である

## 5. ユーザーストーリーと受け入基準

### US-01: 指定距離の周回コースを得る

> ランナーとして、距離を指定して周回コースを見たい。
> なぜなら、走る前にコースを決めておきたいから。

受け入基準:

- **AC-01-1** 起点と目標距離を指定して実行すると、コースが1本地図上に表示される
- **AC-01-2** 表示されたコースの**合計距離**（ループ距離 + 接近距離 × 2）が、
  目標距離の ±300m 以内である
  - 版1.0 はループ距離で判定していた。ユーザーが走るのは合計距離なので判定対象を変えた。
    自宅座標では両者の差は 1.4m しかないが（接近距離 0.7m の実測）、
    差が無視できる保証は起点座標次第であり、式として合計距離を正典とする
- **AC-01-3** 接近距離に応じて3段に分岐する

  | 接近距離 | 挙動 |
  |----------|------|
  | 〜50m | 通常どおり結果を表示する。追加のメッセージは出さない |
  | 50m 〜 300m | 結果を表示するが、接近距離を画面に明示する（AC-02-5）。**この帯では AC-01-2 の ±300m を精度保証の対象外とする** |
  | 300m 超 | 結果を表示せず拒否する。メッセージで代替行動を名指しする |

  - 300m 超のメッセージは、起点が悪いことを述べるだけでなく
    **「最寄りの道路上をクリックしてください」と次にすべき操作を名指しする**。
    例:「起点が道路から 420m 離れています。最寄りの道路上をクリックしてください。」
  - 50〜300m を保証対象外とする理由は 4.4（直線近似の過小評価が誤差予算を食うため）。
    画面上でも「この起点では距離の精度が落ちます」と伝える
  - 実測では自宅座標の接近距離は 0.7m で、通常はこの分岐に入らない（4.4）。
    3段構成は道路から離れた地点をクリックした場合の保険である
- **AC-01-4** ±300m 以内の候補が得られなかった場合、距離誤差が最小の候補を表示し、
  条件を満たすコースがなかった旨のメッセージを表示する
- **AC-01-5**（新）**合計距離が目標距離の3倍を超える候補は異常値として除外する。**
  除外した候補は AC-01-4 の妥協パス（誤差最小の候補を出す経路）でも表示しない
  - 根拠: 暫定座標で目標 5km に対し約 415km・416km のルートが2件返った
    （23 回中2件 = 8.7%。実測値は 416,451.3m と 414,672.8m。FINDINGS スパイク2）。
    生の平均・標準偏差はこの2件で破壊されており、統計にも表示にも載せてはならない
  - **AC-01-4 で「誤差最小」を選ぶ際も、除外は先に適用する。**
    妥協して出すコースが 415km であってはならない
  - 除外により候補が0件になった場合は AC-06-3 の扱いとする

### US-02: 目標との差を知る

> ランナーとして、コースが目標距離とどれだけ違うか知りたい。
> なぜなら、走りながら調整する量を把握したいから。

受け入基準:

- **AC-02-1** **合計距離**がキロメートル単位（小数第2位まで）で表示される
- **AC-02-2** 距離誤差（合計距離 − 目標距離）がメートル単位で、符号付きで表示される
- **AC-02-3** **合計距離**が目標より短い場合、不足分を起点付近で調整する案内が表示される
- **AC-02-4** **合計距離**が目標より長い場合、超過分を手前で切り上げる案内が表示される
- **AC-02-5**（新）**接近距離が 50m を超える場合、その値を画面に表示し、
  ずれの向きも併せて伝える**
  - ずれの向きとは「表示は過小評価であり、実走は表示より長くなる」こと（4.4）。
    例:「起点から道路まで 120m あります。往復ぶん 240m を合計距離に含めていますが、
    直線距離での計算なので、実際はこれより長くなります。」
  - 50m 以下では表示しない。実測 0.7m（自宅、99回すべて同一値）なので、
    通常運用では画面に出ないメッセージである
  - 向きを伝えるのは、ユーザーが走行中に行う調整（AC-02-3 / AC-02-4）の
    方向を誤らせないため。過小評価であることを知らせないと、
    「足りない」と思って余分に走る判断をしてしまう

### US-03: 走りやすいコースを得る

> ランナーとして、坂や階段の少ないコースを走りたい。
> なぜなら、練習の目的は距離を積むことであり、坂で消耗したくないから。

受け入基準:

- **AC-03-1** 生成されるコースに階段が含まれない
  - `round_trip` と `avoid_features:[steps]` は併用できることを実測で確認済み
    （FINDINGS スパイク1、200 OK）。ただし効果は OSM のタグ付けに依存するため
    best effort であり、階段回避が実際に効いているかは未検証（4.7）
- **AC-03-2** 距離条件（合計距離 ±300m）を満たす候補が2件以上ある場合、
  そのうち獲得標高が最小の候補が選ばれる
  - 獲得標高（`ascent`）は `elevation:true` で本体のレスポンスに含まれ、
    追加の API 呼び出しは不要（FINDINGS スパイク1。実測値 67.2m、
    周回なので `descent` と一致）
  - 獲得標高は**候補間の相対比較にのみ使う。** ORS の標高は 30m 解像度程度で
    絶対値に誤差があるが、本 AC が要求するのは相対比較だけである
- **AC-03-3** 選ばれたコースの獲得標高が画面に表示される
  - **これはループ区間のみの値である旨を注記する。**
    接近区間の標高はレスポンスに存在せず、加算できない（4.5）。
    注記なしで表示すると、接近距離が大きい起点で実態と合わない値になる

### US-04: コースを覚えて走り出す

> ランナーとして、コースの要点を把握したい。
> なぜなら、走行中はスマートフォンを見ずに走りたいから。

受け入基準:

- **AC-04-1** チェックポイントが最大5件表示される
- **AC-04-2** 各チェックポイントに、起点からの距離と方向転換の向きが表示される
  - **起点からの距離は「接近距離 + ループ上の累積距離」とする。**
    API が返す累積距離はルート始点を 0 とするため、接近距離ぶんのオフセットを
    加算しないと、ユーザーが自宅から測る距離と食い違う
  - 実測ではオフセットは 0.7m で表示上ほぼ影響しないが（4.4）、
    起点によっては効くため式として定める
- **AC-04-3** 方向転換が6か所以上ある場合、起点からの距離が均等になるよう5件に間引かれる
- **AC-04-4** **チェックポイントの標準形は「起点から 1.2km 地点を左折」とし、
  地点名は取得できた場合のみ併記する。名前がないことは異常として扱わない**
  - 版1.0 は「取得できた場合は併記」と書いていたが、実測では
    **86 step のうち 82 件（95%）で `name` が文字列 `"-"`** であり、
    併記できないのが通常だった（FINDINGS スパイク1）。
    名前は稀なボーナスであり、UI の主役にしてはならない
  - `"-"` は「名前なし」を意味する ORS の値であり、そのまま画面に出さない
  - 方向転換の種別（maneuver）は実測で 0=左折, 1=右折, 2=鋭い左, 3=鋭い右,
    4=緩い左, 5=緩い右, 6=直進, 10=到着, 11=出発, 12=左側維持 を観測した。
    未観測の種別（13、ラウンドアバウト系）が来る前提とし、
    **知らない種別は方向転換として扱わない**側に倒す

### US-05: 起点を指定する

> ランナーとして、出発地点を自分で指定したい。
> なぜなら、自宅の玄関を正確に起点にしたいから。

受け入基準:

- **AC-05-1** 地図上をクリックすると、その位置が起点として設定される
- **AC-05-2** 設定された起点が地図上にマーカーで表示される
- **AC-05-3** 起点を指定せずに実行しようとした場合、指定を促すメッセージが表示される

### US-06: 失敗時に状況を理解する

> ランナーとして、うまくいかなかったときに理由を知りたい。
> なぜなら、自分で対処するか諦めるかを判断したいから。

受け入基準:

- **AC-06-1** API 呼び出しが失敗した場合、失敗した旨のメッセージが表示される
  - 実測の失敗率は 4.6。404 は自宅で 1/103、暫定座標で 2/23 = 8.7%。
    信頼区間の上限が 5.3%〜26.8% あるため、必ず起こるものとして実装する
- **AC-06-2** API キーが未設定の場合、設定が必要である旨のメッセージが表示される
- **AC-06-3** 候補が1件も取得できなかった場合、その旨のメッセージが表示される
  - AC-01-5 の異常値除外の結果として0件になった場合も、この扱いとする
- **AC-06-4** いずれの異常時も、アプリが停止せず再実行できる状態を保つ

### US-07: 起点の再指定を省く

> ランナーとして、2回目以降は起点を指定せずに使いたい。
> なぜなら、走る直前の操作を最小限にしたいから。

受け入基準:

- **AC-07-1** 起点を指定すると、その座標がブラウザに保存される
- **AC-07-2** 次回アプリを開いたとき、保存された起点が復元され地図上に表示される
- **AC-07-3** 復元された起点は、地図をクリックすることで上書きできる
- **AC-07-4** 保存された起点がない初回起動時は、起点の指定を促す状態で表示される

永続化方式はスパイク未実施であり、この US に実測の裏付けはない（4.7）。

### US-08（新規）: 別のコースを見る

> ランナーとして、提案されたコースが気に入らないときに別の候補を見たい。
> なぜなら、同じコースばかりだと飽きるし、その日の気分に合わないこともあるから。

版1.1 で追加した。版1.0 では「前回と違うコースの提示」を
「履歴の保存が前提」として全面的に対象外にしていたが、実測により
**同一セッション内であれば履歴なしで、かつ API を追加で叩かずに実現できる**
ことが分かったため、範囲を限定して受け入れた（FINDINGS「設計に効いた発見」6）。

受け入基準:

- **AC-08-1** 引き直しを操作すると、次に良い候補が表示される
  - 「次に良い」とは、在庫（合計距離 ±300m を満たす候補）を獲得標高の昇順に
    並べたときの次の1本を指す。選択規準は初回表示と同一であり、
    ランダムではない（6節の順序をそのまま使う）
- **AC-08-2** 引き直しでは外部 API を呼び出さない
  - 初回実行で得た在庫から出す。根拠: 15 本投げると ±300m を満たす候補が
    **平均 5.0 本**得られ（n=30, 95%CI 2.9〜7.7）、
    **2本以上得られる確率は 98.1%**（FINDINGS スパイク4「在庫数」）。
    引き直しのたびに API を叩く設計にすると毎分制限（約40回）に接触するが、
    在庫方式ならその問題が消え、引き直しが瞬時になる
- **AC-08-3** 在庫を出し切った場合、それ以上の候補がない旨を表示する
  - 在庫は平均 5.0 本だが下限側の信頼区間は 2.9 本であり、
    少ない回数で尽きる場合がある。尽きたことを黙って同じコースを再表示してはならない
- **AC-08-4** 引き直しで表示される候補も、合計距離 ±300m を満たす
  - 在庫は定義上 ±300m を通過済みなので自動的に満たされる。
    在庫が尽きたときに ±300m 未満の候補で埋めることは**しない**（AC-08-3 を優先）。
    距離の正確さが本アプリの中核価値であり、目先の「もう1本」と引き換えにしない
- 対象は同一セッション内のみ。ブラウザを閉じて開き直した場合、
  在庫は失われ同じコースが出る可能性がある（3.2）

## 6. 候補選択のロジック

US-01 と US-03 を両立させるため、以下の順で絞り込む。

1. **シードを変えて候補を 15 本、並列に生成する**（回数の根拠は 7節）
2. **合計距離が目標の3倍を超える候補を異常値として捨てる**（AC-01-5）
3. **合計距離**の距離誤差が ±300m 以内の候補に絞る（これを在庫と呼ぶ）
4. 在庫のうち、獲得標高が最小のものを選ぶ
5. 手順3で在庫が0件になった場合、手順2を通過した全候補のうち
   距離誤差が最小のものを選び、条件未達である旨を表示する（AC-01-4）
6. 引き直し（US-08）では、在庫を獲得標高の昇順に並べた次の1本を出す。
   このとき API は呼ばない

距離条件を先に適用する理由は、本アプリの中核価値が距離の正確さにあるため。
坂の少なさは、距離条件を満たした上での最適化とする。

**候補の生成方式は単純方式（シードを変えて N 本投げ、その中から選ぶ）とする。**
2段方式（1本目で距離比を測り、補正した length で2本目を投げる）は採用しない。
判定は実測前に固定した決定ルールに基づく（FINDINGS「決定ルールと判定」）。

- 単純方式の命中率 33.3%（n=30, 95%CI 19.2%〜51.2%）
- 2段方式の命中率 53.3%（n=30, 95%CI 36.1%〜69.8%）
- **命中率はほぼ倍だが呼び出しもちょうど倍。** 1呼び出しあたりの命中数は
  0.333 本（単純）対 0.300 本（2段）で、単純方式が 11.1% 効率的
- 同じ予算（20回）での在庫は 6.7 本（単純）対 6.0 本（2段）

**補正係数をコードに定数として持つことはできない。** 平均比は 0.9912（n=30）で
偏りがなく、問題は標準偏差 14.5pt（5km に対して ±725m）という分散である。
係数では分散は縮まらないため、補正という手段が原理的に効かない
（FINDINGS「設計に効いた発見」1、および「反証された推測」1・2）。

**スナップ距離はシードに依存しない**ため、1本目の応答で接近距離を判定でき、
AC-01-3 の 300m 超に該当する場合は残りを投げずに打ち切れる（FINDINGS 同 5）。

### 7.1 API 呼び出し回数を 10 回から 15 回に変えた理由

**版1.0 の「10回以内」には根拠がなかった。** 実測前に「多すぎない程度」として
置いた数値であり、命中率も在庫の必要数も分かっていなかった。記録として残す。

15 回に変えた根拠は4つ。

1. **決定ルールの閾値を満たす最小水準に近い。** 単純方式の命中率の Wilson 下限
   `p_lo = 19.2%`（n=30, 命中 10/30）を使うと、N 本投げて1本以上命中する確率は
   `1-(1-p_lo)^N`。**N=10 では 88.1%、N=15 では 95.9%。**
   スパイク時に事前固定した判定基準は「90% を超えること」であり、
   **10 回はこれを満たさず、15 回は満たす。**
   （15回の 95.9% は FINDINGS「決定ルールと判定」に記載。
   10回の 88.1% は同じ式で本書が算出した値）
2. **引き直し（US-08）に必要な在庫が取れる。** 15 本で ±300m を満たす候補が
   平均 5.0 本（95%CI 2.9〜7.7）、2本以上が 98.1%（FINDINGS スパイク4「在庫数」）。
   引き直しを API なしで成立させるには2本以上が必要
3. **毎分制限に余裕がある。** 約 40 回に対して 15 回は 37.5% で、
   1分以内に2回実行しても 30 回で収まる
4. **無料枠を圧迫しない。** 無料枠 2000 回/日に対し、15 回なら1日 133 回実行できる。
   個人が走る前に使う頻度では過剰に十分

20 回にしなかった理由: 在庫は 6.7 本に増えるが（FINDINGS 同表）、
2本以上の確率は 98.1% → 99.7% の改善にとどまり、毎分制限の余裕を削る。
15 回で要件を満たすため増やさない。

**この数値は目標距離 5km・起点2点での実測に基づく（4.7）。**
他の距離で命中率が下がれば 15 回では足りなくなる。再測定が必要。
