# 設計書: 周回ランニングコース提案アプリ（RunLoop）

- 版: 1.0
- 作成日: 2026-08-05
- 根拠: [requirements.md](requirements.md)（版1.2・確定）と [spike/FINDINGS.md](../spike/FINDINGS.md)
- 技術選定の記録: [adr/](adr/)（0001〜0004）

この文書は「何をどこに置き、なぜそうするか」を決める。コードは書かない。
実装時は受け入基準（AC-xx）を正典とし、本書はその実現手段を示す。

**数値の扱い。** 本書に出る数値はすべて出所を書く。
`実測` は FINDINGS の該当箇所を参照し、`設計判断` は実測がないことを明示する。
`要検証` はスパイク未実施で、実装中または実装後に確かめる項目である（末尾 11 節に一覧）。

**FINDINGS の訂正について。** FINDINGS には訂正節が2つある（初回と第2次）。
本書が引用する数値のうち、2段方式の効率（1呼び出しあたり命中数）と
スパイク3の命中率は**訂正後の値**を使う。詳細は FINDINGS 末尾の
「訂正（2026-08-05 追記・第2次）」を参照。

## 1. モジュール構成と責務

### 1.1 全体像

```
runloop/                  ← 本体パッケージ（Streamlit に依存しない層）
  models.py               データ構造。他モジュールに依存しない
  geo.py                  座標計算（haversine、方位）。純関数のみ
  ports.py                外部依存の境界。Protocol とドメイン例外
  ors/
    client.py             ORS の HTTP 呼び出しとステータス→例外の翻訳
    mapper.py             ORS の GeoJSON → ドメインオブジェクトへの変換
  generation.py           候補生成（プローブ → 接近ゲート → 残りを並列）
  selection.py            候補選択（異常値除外 → 在庫 → 獲得標高最小）
  checkpoints.py          方向転換の抽出と5件への間引き
  messages.py             画面文言の生成（距離差分、接近距離、失敗）
  session.py              在庫と引き直しカーソルの状態（純データ）
  persistence.py          起点の永続化ポート（方式は ADR-0004 で保留）
  config.py               設定値と定数（許容誤差、本数、閾値、APIキーの読み出し）

ui/                       ← Streamlit 層（ここだけが Streamlit を import する）
  app.py                  画面の組み立てとイベント処理
  map_view.py             folium での地図描画

tests/                    単体テストと fixtures/（実レスポンスの JSON）
spike/                    検証用の使い捨てスクリプト。本体から参照しない
```

### 1.2 各モジュールの責務と、そう分けた理由

| モジュール | 責務 | なぜ分けるか |
|---|---|---|
| `models.py` | `Candidate` `Turn` `Checkpoint` `SelectionResult` などのデータ構造と、その計算プロパティ | 判定値と表示値を1か所から出すため。合計距離を各所で再計算すると食い違う（2.2） |
| `geo.py` | 2点間距離（haversine）、方位の言い換え | 接近距離の算出は AC-01-2 の判定に直結する。純関数にして単体テストで固定する |
| `ports.py` | `RouteProvider` Protocol、ドメイン例外の定義 | 外部 API を差し替え可能にする（非機能要件・保守性）。上位層に `requests` と HTTP ステータスを持ち込まない（3節） |
| `ors/client.py` | ORS への1回の呼び出し。リトライ判断とステータスの翻訳 | 「1回の呼び出し」に責務を閉じる。並列化と本数の管理は `generation.py` の仕事 |
| `ors/mapper.py` | GeoJSON の読み取り。`"-"` の正規化、maneuver 種別の変換 | ORS のレスポンス形式に依存する知識をここだけに閉じる。プロバイダを足すときに写す範囲が明確になる |
| `generation.py` | 15本の生成、接近ゲートでの打ち切り、部分的失敗の吸収 | 「何本投げるか」「いつ諦めるか」は API 利用の非機能要件（7節）に直結する判断で、選択ロジックとは別問題 |
| `selection.py` | 6節の順序どおりの絞り込み | ここが本アプリの中核価値（距離の正確さ）。外部依存ゼロの純関数にして、テストで順序を固定する |
| `checkpoints.py` | 方向転換の抽出、接近距離のオフセット加算、5件への間引き | AC-04 の4基準がすべてここに集まる。選択ロジックと混ぜない |
| `messages.py` | 文言の生成（表示はしない） | AC-01-3 / AC-01-4 / AC-02-3〜5 は「何と表示するか」が基準そのもの。文言を返す純関数にすればテストできる |
| `session.py` | 在庫・カーソル・実行条件の保持 | US-08 の状態遷移を Streamlit なしでテストするため |
| `persistence.py` | 起点の読み書きポート | 方式が未決（ADR-0004）。ポートだけ決めて実装を後から差す |
| `config.py` | 定数と設定 | ±300m、15本、50m/300m といった要件由来の数値をコード中に散らさない。値の変更が要件の変更であることを明示する |
| `ui/app.py` | 入力・実行・表示・引き直しの配線 | Streamlit 画面は手動確認とする方針（CLAUDE.md）。自動テストできない層を薄く保つ |

**設計の中心にある1つの規律。** `ui/` 以外は Streamlit を import しない。
理由は、Streamlit の画面は自動テストしない方針であり、
ロジックが Streamlit に依存すると「テストできない範囲」が広がるため。

**補足（Streamlit 固有の話）。** Streamlit はボタンを押すたびに
スクリプト全体を上から再実行する仕組みで、通常の変数は毎回消える。
消えてほしくない状態は `st.session_state` という辞書に入れる。
本設計では `session.py` の純データを `st.session_state` に1つ置くだけにして、
状態の在り処を1か所にする（6節）。

### 1.3 依存の向き

```
ui/  ──▶ generation / selection / checkpoints / messages / session / persistence
              │                                     │
              ▼                                     ▼
           ports.py ◀── ors/client.py ── ors/mapper.py
              │
              ▼
        models.py ◀── geo.py
```

`models.py` は何にも依存しない。`ors/` は `ports.py` の Protocol を満たすだけで、
上位から名前で参照されない（`config.py` が組み立てて注入する）。
**理由:** 将来 ORS を別サービスに替えるとき、変更が `ors/` と `config.py` に収まる（非機能要件・保守性、ADR-0001）。

## 2. データ構造

### 2.1 一覧

| 型 | 種別 | 主なフィールド |
|---|---|---|
| `LatLon` | 不変値 | `lat` `lon` |
| `RouteQuery` | 不変値 | `origin: LatLon` `target_m: int` `points: int = 3` `avoid_steps: bool = True` |
| `ProviderRoute` | 不変値（プロバイダの生の成果） | `seed` `loop_m` `ascent_m` `descent_m` `snapped_start: LatLon` `geometry: tuple[LatLon, ...]` `steps: tuple[RawStep, ...]` |
| `Candidate` | 不変値（ドメインの候補） | `seed` `loop_m` `approach_m` `ascent_m` `descent_m` `target_m` `geometry` `turns: tuple[Turn, ...]` |
| `Turn` | 不変値 | `direction: TurnDirection` `cumulative_loop_m` `position: LatLon` `name: str \| None` |
| `Checkpoint` | 不変値（表示用） | `order` `distance_from_origin_m` `direction` `name: str \| None` `position` |
| `ApproachVerdict` | 列挙 | `OK` / `WARN` / `REJECT` |
| `GenerationOutcome` | 不変値 | `candidates` `approach_m` `verdict` `failures: Mapping[str, int]` `calls_consumed` `aborted_early: bool` |
| `SelectionResult` | 不変値 | `chosen: Candidate \| None` `stock: tuple[Candidate, ...]` `outcome: SelectionOutcome` `degenerate_count` |
| `SelectionOutcome` | 列挙 | `IN_TOLERANCE` / `COMPROMISED` / `NO_CANDIDATE` / `ORIGIN_REJECTED` |
| `RunSession` | 可変（1つだけ） | `query` `stock` `cursor` `approach_m` `outcome` `generated_at` |

すべて `frozen=True` のデータクラス（`RunSession` を除く）。
**理由:** 候補は生成後に書き換えない。不変にすると、在庫を並べ替えても
元の候補が壊れないことが型で保証され、テストの前提が単純になる。

### 2.2 合計距離は `Candidate` の計算プロパティにする

`Candidate` は次を**プロパティとして**持つ。フィールドとして事前計算しない。

| プロパティ | 定義 | 対応 AC |
|---|---|---|
| `total_m` | `loop_m + approach_m * 2` | AC-01-2 / AC-02-1 |
| `error_m` | `total_m - target_m` | AC-02-2 |
| `abs_error_m` | `abs(error_m)` | AC-01-4 |
| `is_within_tolerance` | `abs_error_m <= 300.0` | AC-01-2 |
| `is_degenerate` | `total_m > target_m * 3` | AC-01-5 |

**なぜ計算プロパティか。** 合計距離は判定（AC-01-2）にも表示（AC-02-1）にも使う。
`selection.py` が局所変数で合計距離を組み立てると、画面が表示する値と
選択が使った値が別の計算経路を通り、片方だけ直したときに食い違う。
候補そのものに1つの定義を持たせれば、判定値と表示値が同一であることが構造で保証される。

**なぜ `target_m` を `Candidate` が持つか。** `error_m` を候補側で出すには目標距離が必要になる。
外から渡す形（`error_of(candidate, target)`）にすると、呼び出し側が
別の目標距離を渡す余地が残る。1回の実行では目標距離は1つなので、
生成時に焼き付けて誤用の余地を消す。

**なぜ `approach_m` を候補ごとに持つか。** 実測では接近距離は起点だけで決まり、
シードに依存しない（自宅座標で 0.7m、99 回すべて同一値。FINDINGS スパイク3
「AC-01-3」＋訂正2）。それでも候補ごとに持たせる理由は2つ。

1. 「シードに依存しない」は ORS の実測事実であって、ドメインの不変則ではない。
   プロバイダを替えたときに前提が崩れても、構造が壊れない側に倒す
2. 全候補で同値になることを**テストで確認できる**（10節）。定数として1か所に
   置くと、この確認が書けない

丸めは行わない。表示の丸め（小数第2位、AC-02-1）は `messages.py` の責務とし、
判定は生の float で行う。**理由:** 表示のために丸めた値で判定すると、
±300m の境界付近で表示と判定が食い違う。

### 2.3 `Turn` と `Checkpoint` を分ける

`Turn` はループ上の方向転換そのもので、**ルート始点からの**累積距離を持つ。
`Checkpoint` は表示用で、**起点からの**距離を持つ（`approach_m + cumulative_loop_m`）。

**なぜ2つに分けるか。** AC-04-2 は「起点からの距離」を求め、
API が返す累積距離はルート始点起点である。同じ「距離」という名前の
異なる基準が1つの型に同居すると、オフセットの二重加算や加算漏れが起きる。
型を分ければ、オフセットを足す場所が `Checkpoint` の生成時の1か所に限定される
（7節）。

### 2.4 `SelectionResult` が在庫を持つ

選択の結果は「選ばれた1本」だけでなく「在庫（獲得標高の昇順）」を返す。
**理由:** 引き直し（AC-08-1）は在庫の次の1本を出す操作であり、
初回選択と同じ順序を使う。並び順を選択側で確定させ、
引き直し側では並べ替えない（AC-08-1 の「ランダムではない」）。

## 3. 外部 API の抽象化

### 3.1 ポート（Protocol）

`ports.py` に1つの Protocol を置く。

```
RouteProvider（Protocol）
    round_trip(origin: LatLon, length_m: int, seed: int, points: int,
               avoid_steps: bool) -> ProviderRoute
```

**責務の境界。** プロバイダは「1本のルートを取ってくる」ことだけを知る。
目標距離、許容誤差 ±300m、異常値の3倍、接近距離の閾値は**一切知らない**。
**理由:** これらは要件由来のドメイン規則であり、プロバイダを替えても変わらない。
プロバイダ側に置くと、実装を足すたびに規則が複製される。

`ProviderRoute` は `snapped_start`（API がルート始点として返した座標）を持つが、
接近距離そのものは持たない。接近距離は `generation.py` が
`geo.haversine(origin, snapped_start)` で算出する。
**理由:** 接近距離は「起点」というアプリ側の概念との差であり、
プロバイダの成果物ではない（4.4）。

抽象化の粒度を「1本の取得」にした理由は、並列化・本数・打ち切りが
API 利用の非機能要件（7節）に属する判断であり、プロバイダごとに
書き直したくないため。15本投げるロジックは `generation.py` に1つだけ置く。

### 3.2 ドメイン例外への翻訳

`ors/client.py` は HTTP の事実を、上位が扱えるドメイン例外に翻訳する。

| 観測した事実 | ドメイン例外 | 意味 | 実測 |
|---|---|---|---|
| キー未設定（呼び出す前に判定） | `ApiKeyMissing` | 設定が必要（AC-06-2） | — |
| 401 / 403（認証） | `ApiKeyRejected` | キーが無効 | 未観測（要検証） |
| 404（`code: 2009`） | `RouteNotFound` | この起点・シードではルートが作れない | 自宅 1/103、暫定座標 2/23（4.6） |
| 429 | `RateLimited` | 毎分制限。枠は消費しない | 直近1分に約40回で発生（FINDINGS スパイク3 C） |
| 5xx / 接続エラー / タイムアウト | `ProviderUnavailable` | 一時的な障害 | 未観測（要検証） |
| 200 だが JSON が想定と違う | `MalformedRoute` | 変換できない | 未観測（要検証） |
| 200 だがルートが目標の3倍超 | **例外にしない** | 候補として返し、選択側で除外（AC-01-5） | 暫定座標 2/23（4.6） |

いずれも共通の基底 `RouteProviderError` を継承する。

**なぜ翻訳するか。** 3つ理由がある。

1. **上位が判断できる語彙にする。** `RouteNotFound` と `RateLimited` は、
   リトライすべきかどうかが正反対である（4節）。HTTP の数字のまま上げると、
   その判断が `generation.py` と `ui/` に散る
2. **差し替え可能性（非機能要件・保守性、ADR-0001）。** 別サービスは
   「ルートなし」を 200 + 空配列で返すかもしれない。
   例外の語彙がドメイン側にあれば、上位のコードは変わらない
3. **無料枠の消費と結びつく判断だから。** 404 は枠を消費し、429 は消費しない
   （4.6.1。FINDINGS の記述を訂正済み）。この差は HTTP ステータスに現れるが、
   意味はドメイン側の関心事である

**異常ルート（415km）を例外にしない理由。** 200 で返る正常なレスポンスであり、
「候補としては使えない」というのは選択基準（AC-01-5）である。
除外を例外にすると、除外件数を数えて AC-06-3 の判定に使う経路が作れない。

**観測値の持ち回し。** `ProviderRoute` と例外は
`ratelimit_remaining`（レスポンスヘッダの残数）を持つ。
**理由:** 無料枠の消費は設計判断の前提（4.6.1）であり、
実運用で前提が崩れたことに気づく手段が必要。画面には出さず、ログに出す。

**ログにキーを出さないこと。** 例外メッセージにリクエストヘッダを含めない
（非機能要件・セキュリティ）。

## 4. 候補生成のフロー

### 4.1 二段投入（プローブ1本 → 残り14本を並列）

```
1. キーの有無を確認          → なければ ApiKeyMissing（AC-06-2）
2. シードを15個決める
3. 1本目（プローブ）を投げる
4. 応答から接近距離を算出     approach_m = haversine(起点, snapped_start)
5. 接近ゲート（AC-01-3）
     > 300m  → 残り14本を投げずに中止。verdict=REJECT で戻る
     50〜300m → 続行。verdict=WARN
     〜50m    → 続行。verdict=OK
6. 残り14本を並列（同時14）で投げる
7. 成功した応答を Candidate に変換して返す。失敗は種類別に数える
```

**なぜ「15本同時」ではなく「1本 → 14本」なのか。**
要件は「15本並列。1本目の応答で接近距離を判定し、300m超なら残りを打ち切る」
（6節）である。15本を同時に投げてから判定すると、
**打ち切りが成立しない。** 送信済みのリクエストは取り消せず、
404 と同様に枠を消費する（4.6.1）。道路から離れた地点をクリックした
1回の操作で15回消費してしまう。未投入なら確実に投げずに済む。

**性能は満たせる。** 1呼び出しの実測は 1.33〜2.64 秒（n=103、
FINDINGS スパイク3 C の個別平均と スパイク4 の所要時間より本書が集計）。
10本同時の壁時計が 2.03 秒（実測）なので、
プローブ 約2秒 + 14本並列 約2秒 = **約4〜5秒**。
10秒以内（7節 性能）に収まる。直列15回は約27秒で要件を破る。

**プローブも候補として使う。** プローブの応答は捨てず在庫に入れる。
**理由:** 呼び出し総数を15回に保つ（7節 API 利用）。
プローブを別枠にすると16回になり、根拠のある数値（7.1）を崩す。

**並列の実現方法。** `requests` は同期のため `ThreadPoolExecutor` を使う
（スパイクで実測した方法と同じ。同時10本でエラー0件）。
`asyncio` + `httpx` に替えない理由は、依存を増やす利益がなく、
実測済みの構成から離れる不利益があるため。

### 4.2 シードの決め方

実行ごとに乱数で15個選ぶ（重複なし）。固定値にしない。

**理由:** 在庫を出し切った後の「もう一度探す」（AC-08-3 の次の行動）で
別の15本が得られる必要がある。シードを固定すると同じ15本が返り、
「別のコースを見たい」（US-08）に応えられない。

シードの範囲は要検証。実測は seed 1〜30 と 1001〜1006、106〜113 のみで、
大きな値での挙動は未確認（FINDINGS 測定の限界）。

### 4.3 リトライ方針（ステータスで分ける）

| 例外 | リトライ | 回数 / 待機 | 理由 |
|---|---|---|---|
| `RateLimited`（429） | **する** | 1回・1秒待機 | 枠を消費しない（4.6.1 で確認済み）ため試行が安い。ただし毎分ウィンドウの制限なので短い待機で回復するとは限らない（**要検証**）。回復しなければ欠測として続行 |
| `RouteNotFound`（404） | **しない** | 0回 | **枠を消費する**（4.6.1。FINDINGS の初回の記述を訂正済み）。加えて同じ起点・同じシード・同じ length では決定的に再現すると考えられ、投げ直す意味がない（決定性は**要検証**） |
| `ProviderUnavailable`（5xx / 接続 / タイムアウト） | する | 1回・即時 | ネットワークの一過性障害を1回だけ吸収する。実測での観測はゼロ（要検証） |
| `ApiKeyMissing` / `ApiKeyRejected` | しない | 0回 | 再試行しても結果が変わらない。即座に AC-06-2 |
| `MalformedRoute` | しない | 0回 | 同じ応答が返る。その1本を欠測として続行 |

**待機を1秒に抑える理由。** 10秒の性能要件（7節）と衝突させない。
429 の回復には毎分ウィンドウの都合で最大60秒かかりうるが、
それを待つと要件を破るので、待たずに「1分ほど待って再実行してください」と
案内する側に倒す（9節）。

**リトライを含めた呼び出し上限。** 無料枠の消費で数えて15回（7節 API 利用）、
実際の送信回数は429のリトライを含めて最大18回とする。
**理由:** 429 は枠を消費しないが毎分制限には触れる（4.6.1）。
消費と送信を別に数えないと、どちらの制限を守っているのか曖昧になる。
18 は 15 + 3（設計判断。実測なし）。

### 4.4 部分的失敗の扱い

15本のうち何本失敗しても、成功した候補で選択を続行する（AC-06-4）。
失敗は種類別に数え（`failures`）、ログに出す。画面には出さない。

**理由:** 15本のうち1〜2本の 404 は実測される正常な範囲であり
（自宅 1/103、暫定座標 2/23。4.6）、ユーザーの行動を変えない情報である。
在庫が減る影響は AC-08-3 のメッセージで結果として伝わる。

全滅（成功0本）なら `NO_CANDIDATE` として AC-06-3 に落とす。

### 4.5 タイムアウト

1呼び出し8秒（設計判断。実測の最大は 2.64 秒）。
**理由:** 10秒の性能要件に対し、応答待ちで無限に固まらないことを優先する。
8秒は「実測の3倍」であり、実測に基づく値ではない。要検証。

## 5. 候補選択のフロー

### 5.1 順序（6節をそのまま実装する）

```
入力: GenerationOutcome（候補・接近距離・verdict）、target_m

1. 接近ゲート
     verdict == REJECT  → SelectionResult(chosen=None, ORIGIN_REJECTED)
                          候補は1本も表示しない（AC-01-3）
2. 異常値除外
     is_degenerate（合計距離 > 目標 × 3）を捨てる（AC-01-5）
     捨てた件数を degenerate_count に残す
3. 除外後が0件      → NO_CANDIDATE（AC-06-3）
4. 在庫を作る
     is_within_tolerance（|合計距離 − 目標| ≤ 300m）の候補（AC-01-2）
     並び順は 獲得標高 昇順 →（同値なら）|距離誤差| 昇順 → seed 昇順
5. 在庫が1本以上   → chosen = 在庫の先頭、IN_TOLERANCE（AC-03-2）
6. 在庫が0件       → 手順2を通過した候補から |距離誤差| 最小を選び、
                      COMPROMISED（AC-01-4）。在庫は空のまま
```

**距離を先に、標高を後にする理由。** 中核価値は距離の正確さである（6節）。
逆順（標高最小を選んでから距離を見る）にすると、
坂がないだけの外れた距離が選ばれる。requirements.md が
「順序が仕様」と明記している点で、実装で最も外しやすい。

**異常値除外を妥協パスより先に置く理由。** AC-01-5 が明示している。
妥協して出すコースが 415km であってはならない
（実測の異常値は 416,451.3m と 414,672.8m。FINDINGS スパイク2）。

**並び順に第2・第3キーを置く理由。** 獲得標高が同値の候補があると、
並び順が実行ごとに変わりうる。引き直し（AC-08-1）は
「次に良い1本」を出す操作なので、順序が決定的でないと
同じ操作で違う結果になり、テストも書けない。
第2キーに距離誤差を選んだのは、距離が中核価値だから。

**境界値の扱い（設計判断。実測なし）。**

| 条件 | 判定 | 理由 |
|---|---|---|
| `abs_error_m == 300.0` | 在庫に**入れる** | AC-01-2 は「±300m 以内」で、以内は境界を含む |
| `total_m == target_m * 3` | 異常値に**しない** | AC-01-5 は「3倍を超える」。ちょうど3倍は超えていない |
| `approach_m == 50.0` | WARN ではなく OK | AC-01-3 の表は「〜50m」で境界を下段に含む |
| `approach_m == 300.0` | REJECT ではなく WARN | 同じ理由。「300m 超」が拒否 |

境界の等号をどちらに入れるかは要件の文面から読み取った判断である。
テストで固定する（10節）。

### 5.2 接近ゲートを選択の外に出さない

接近ゲートの判定自体は `generation.py`（打ち切りのため）で行うが、
**表示するかどうかの判断は `selection.py` に置く。**

**理由:** 「300m 超なら結果を表示しない」は選択の結論（AC-01-3）であり、
生成の都合ではない。生成側が候補を0本にして返すと、
「起点が悪い」と「ルートが見つからない」（AC-06-3）が
画面上で区別できなくなる。`ORIGIN_REJECTED` と `NO_CANDIDATE` を
別の結論として持つ。

## 6. 在庫と引き直しの状態管理（US-08）

### 6.1 状態

`RunSession`（`session.py`）が1つだけ状態を持つ。

| フィールド | 内容 |
|---|---|
| `query` | 起点と目標距離（在庫の有効性の判定に使う） |
| `stock` | 在庫（獲得標高の昇順。生成後は不変） |
| `cursor` | 現在表示している位置（0 始まり） |
| `approach_m` | この実行の接近距離（全候補共通） |
| `outcome` | `IN_TOLERANCE` / `COMPROMISED` など |
| `generated_at` | 生成時刻（ログとデバッグ用） |

Streamlit 層はこれを `st.session_state["run"]` に1つ置くだけにする。

**理由:** Streamlit は操作ごとにスクリプトを再実行するため、
在庫を通常の変数に置くと毎回消えて API を呼び直すことになり、
AC-08-2（引き直しで API を呼ばない）が守れない。
一方で状態を複数のキーに分けると（在庫・カーソル・起点を別々に置くと）
片方だけ更新される事故が起きる。1つの不変オブジェクトにまとめて
差し替えるだけにする。

### 6.2 遷移

| 操作 | 挙動 | 対応 AC |
|---|---|---|
| 実行（探す） | 15本投げて在庫を作る。`cursor = 0` | AC-01-1 |
| 引き直し | `cursor + 1` が在庫内なら進める。**API は呼ばない** | AC-08-1 / AC-08-2 |
| 引き直し（在庫の末尾） | `cursor` を動かさず「これ以上の候補がない」と表示 | AC-08-3 |
| 起点または目標距離が変わった | 在庫を破棄する（`RunSession` を捨てる） | — |
| もう一度探す | 新しいシードで再実行（API を呼ぶ操作として明示） | AC-08-3 の次の行動 |

**在庫を条件変更で破棄する理由。** 目標 5km の在庫は 3km の ±300m を
満たさない。条件が変わった在庫から出すと AC-08-4（引き直しでも ±300m）が壊れる。
`query` を在庫の鍵として持つのはこの判定のためである。

**妥協パス（`COMPROMISED`）では在庫が空になる。** 在庫は定義上
±300m を通過した候補だけなので、誤差最小の1本は在庫に入れない。
結果として引き直しは即「候補がない」（AC-08-3）になる。
**理由:** AC-08-4 が「在庫が尽きたときに ±300m 未満の候補で埋めることはしない」と
明示している。目先の「もう1本」と距離の正確さを引き換えにしない。

**カーソルは前進のみ。** 「前の候補に戻る」は要件にないため実装しない。

### 6.3 在庫の見込みと、尽きる頻度

15本で ±300m を満たす候補は平均 5.0 本、2本以上得られる確率 98.1%
（FINDINGS スパイク4「在庫数」）。引き直しは在庫方式で成立する（AC-08-2）。

**ただしこの 98.1% は命中率の点推定（33.3%）で計算された値である。**
決定ルール（ADR-0003）が使った Wilson 下限 19.2% で同じ計算をすると
2本以上は **81.4%**、期待在庫は 2.9 本になる（本書算出。
FINDINGS 第2次訂正の補足に転記した）。
悲観側では**5回に1回は引き直しが1回もできない**可能性がある。

設計への反映は2つ。

1. AC-08-3 のメッセージは例外処理ではなく通常の経路として作る。
   「尽きた」表示は珍しくない
2. 尽きたときの次の行動（もう一度探す）を同じ画面に置く

在庫の実際の分布は**要検証**（起点2点・5km のみの実測。4.7）。

## 7. チェックポイントの抽出と間引き

### 7.1 抽出

ORS の `segments[].steps[]` から `Turn` を作る。

```
1. instructions を有効にして呼び出す（steps を得るため）
2. 各 step を順に見て、累積距離を積む
     cumulative = それまでの step の distance の合計（= その step の開始点）
3. maneuver 種別が「方向転換6種」のものだけ Turn にする
4. 座標は step の way_points[0] を geometry から引く（地図のマーカー用）
5. name が "-" なら None に正規化する
```

**方向転換として扱う種別（ホワイトリスト）。**

| type | 意味 | 方向転換か |
|---|---|---|
| 0 | 左折 | ○ |
| 1 | 右折 | ○ |
| 2 | 鋭い左 | ○ |
| 3 | 鋭い右 | ○ |
| 4 | 緩い左 | ○ |
| 5 | 緩い右 | ○ |
| 6 | 直進 | × |
| 10 / 11 | 到着 / 出発 | × |
| 12 | 左側維持 | × |
| 未観測（13、ラウンドアバウト系） | 不明 | **×** |

**ホワイトリストにする理由。** AC-04-4 が「知らない種別は方向転換として
扱わない側に倒す」と定めている。ブラックリスト（既知の非転換だけ除く）にすると、
未観測の種別が来たときに「起点から 2.1km 地点を**不明**」のような
案内が出る。走行中に確認できない案内は、無いほうがよい。

**`"-"` を None にする理由。** `"-"` は ORS の「名前なし」を表す値であり
（実測 82/86 = 95%。FINDINGS スパイク1）、そのまま画面に出すと
道の名前として読めてしまう（AC-04-4）。
名前がないことは異常ではないので、警告もログも出さない。

### 7.2 起点からの距離（接近距離のオフセット）

```
distance_from_origin_m = approach_m + cumulative_loop_m
```

**なぜオフセットが必要か。** API の累積距離はルート始点（スナップ先）を 0 とする。
ユーザーは自宅から測る（AC-04-2）。加算しないと、
接近距離ぶんだけ全チェックポイントが手前にずれる。

実測では 0.7m なので表示（0.1km 単位）には現れないが、
道路から離れた起点では効く。**式として定める**のは AC-04-2 の要求である。

**加算する場所を1か所に限定する。** `Checkpoint` の生成時のみ。
`Turn` は生の累積距離しか持たない（2.3）。
**理由:** 二重加算と加算漏れは、どちらも「0.7m のずれ」では気づけず、
接近距離の大きい起点で初めて露見する。型で場所を固定する。

なお接近区間の**道**は描けない（4.5。レスポンスに存在しない）。
チェックポイントの座標はループ上の点のみである。

### 7.3 間引き（AC-04-3）

方向転換が6件以上のとき、**起点からの距離が均等になるよう5件**選ぶ。

```
1. ループ長を6等分し、目標距離を5つ作る
     t_i = approach_m + loop_m * i / 6     (i = 1..5)
2. 各 t_i に最も近い Turn を選ぶ
3. すでに選ばれた Turn は選ばない（次に近いものを取る）
4. 起点からの距離の昇順に並べ、order を 1..5 で振る
```

**なぜ「均等な目標距離への最近傍」か。** AC-04-3 の文面が
「起点からの距離が均等になるよう」であり、方向転換の重要度（角度の鋭さ、
道の大きさ）は基準に入っていない。等間隔の目標に寄せるのが最も素直で、
結果が決定的になる。

**却下した案。** ①先頭5件を取る → 前半だけの案内になり、コースを覚えられない。
②角度の鋭い5件 → 仕様にない基準を持ち込む。実測では左右折が 68/86 で
多数あり、鋭さの分布を根拠にできる材料もない。

方向転換が5件以下ならすべて出す（AC-04-1 の「最大5件」）。
0件のときは何も出さない（周回の形によっては起こりうる。異常ではない）。

**間引きは通常の経路である。** 実測では 86 step のうち方向転換6種が **76 件**あった
（points=5 の1本。内訳は FINDINGS 第2次訂正の補足2）。
5件以下で済むケースを標準と考えて実装しない。

**要検証。** 実測は `instructions: false`（スパイク4）または points=5 の
1本（スパイク1）でのみ steps を確認している。本体は points=3 と
`instructions: true` の組み合わせで動かすため、step 数・名前の割合・
maneuver の分布が同じとは限らない（FINDINGS 第2次訂正の補足）。
最初の実装タスクで実データを1件取得し、`tests/fixtures/` を更新する。

## 8. 起点の永続化

### 8.1 ポートだけ先に決める

`persistence.py` に読み書きの境界を置く。

```
OriginStore（Protocol）
    load() -> LatLon | None
    save(origin: LatLon) -> None
    clear() -> None
```

`ui/app.py` はこの Protocol にしか触らない。

| 状況 | 挙動 | 対応 AC |
|---|---|---|
| 起動時に `load()` が座標を返す | 地図に復元表示 | AC-07-2 |
| 起動時に `load()` が None | 起点の指定を促す | AC-07-4 |
| 地図がクリックされた | `save()` して表示を更新 | AC-07-1 / AC-07-3 |

### 8.2 方式は未決（ADR-0004・要検証）

**永続化方式はスパイク未実施であり、この US に実測の裏付けがない**
（requirements 4.7 が明示）。方式の決定は ADR-0004 で保留した。

`st.session_state` は使えない。Streamlit のセッション状態はブラウザを
閉じると消え、AC-07-2（次回起動時に復元）を満たさない（CLAUDE.md の注意点）。

候補と、それぞれの未確認点は ADR-0004 に書いた。要点だけ再掲する。

| 方式 | 主な懸念 |
|---|---|
| ブラウザの localStorage（コンポーネント経由） | 依存パッケージの追加が必要（CLAUDE.md により事前確認）。初回描画で値が返らない可能性 |
| URL のクエリパラメータ | **自宅座標が URL に載る。** 共有・履歴で漏れる |
| Cookie | 書き込みにコンポーネントが必要。読み出しのみなら標準機能で可 |
| サーバ側のファイル | 「ブラウザに永続化」という要件から外れる。Streamlit Community Cloud では再起動で消える |

**当面の実装方針。** `OriginStore` のセッション内実装（保存しない実装）を先に作り、
US-07 は方式決定後の最後のタスクにする。
**理由:** US-01〜US-06 と US-08 は永続化に依存しない。
未検証の方式を先に入れて全体の構造を歪めるより、ポートを固定して後から差す。
このとき AC-07-1〜4 は未達であることを明示する（黙って満たしたつもりにしない）。

**プライバシーの扱い。** 保存する座標は自宅である。
どの方式でも「URL・ログ・エラーメッセージに座標を出さない」を守る。
スパイクの生データが座標を記録していないのと同じ理由である。
座標の丸めはしない（AC-05-1 の「玄関を正確に」と衝突するため）。

## 9. エラー処理とユーザーへの伝達

### 9.1 対応表

| 状況 | 画面 | AC |
|---|---|---|
| キー未設定 | 「API キーが設定されていません」＋設定場所 | AC-06-2 |
| キーが無効（401/403） | 同上（キーの確認を促す） | AC-06-2 |
| 起点が未指定のまま実行 | 「地図をクリックして起点を指定してください」 | AC-05-3 |
| 接近距離 > 300m | 結果を出さない。「起点が道路から 420m 離れています。最寄りの道路上をクリックしてください。」 | AC-01-3 |
| 接近距離 50〜300m | 結果は出す。接近距離と、**ずれの向き**（実走は表示より長くなる）を明示 | AC-02-5 |
| 全滅（成功0本） | 「コースの候補が得られませんでした」＋起点を道路寄りにする案内 | AC-06-3 |
| 異常値除外で0件 | 同上（AC-06-3 の扱い） | AC-01-5 / AC-06-3 |
| 在庫0件（妥協パス） | 誤差最小の1本を出し、「条件（±300m）を満たすコースが見つかりませんでした」 | AC-01-4 |
| 429 が残った | 「呼び出しが混み合っています。1分ほど待って再実行してください」 | AC-06-1 |
| 5xx・接続不能・タイムアウト | 「地図サービスに接続できませんでした」＋再実行の案内 | AC-06-1 |
| 予期しない例外 | 「予期しないエラーが発生しました」。入力は保持し、再実行できる状態を維持 | AC-06-4 |

### 9.2 方針

**文言は `messages.py` に集約する。** 画面に文字列リテラルを書かない。
**理由:** AC-01-3 / AC-01-4 / AC-02-3〜5 は文言の内容が受け入基準そのもの
（「代替行動を名指しする」「ずれの向きを伝える」）。
純関数が文言を返す形にすれば単体テストで固定できる（10節）。
Streamlit 画面は手動確認とする方針なので、画面に文言を埋めるとテストできない。

**メッセージは必ず次の行動を含める。** 300m 超が「最寄りの道路上をクリック」を
名指しするのは AC-01-3 の明示的な要求である。他のメッセージも同じ形にそろえる。
**理由:** US-06 の目的は「自分で対処するか諦めるかを判断したい」であり、
状態の報告だけでは判断できない。

**接近距離 50〜300m では、精度が落ちることも伝える。** この帯では
±300m は保証の対象外である（AC-01-3、理由は 4.4）。

**アプリを止めない。** どの経路でも例外を画面外に漏らさず、
入力（起点・目標距離）を保った状態で再実行できるようにする（AC-06-4）。
`ui/app.py` の実行ハンドラで `RouteProviderError` とその他の例外を
それぞれ捕まえる。**理由:** Streamlit は未捕捉の例外でトレースバックを
画面に出して以降の描画を止める。それは AC-06-4 に反する。

**ログと画面を分ける。** 例外の型・ステータス・残数・失敗の内訳はログへ。
画面には行動可能な文言だけ。**理由:** ユーザーは走る直前のスマートフォンで
これを読む（4.3）。HTTP ステータスは行動を変えない。

### 10.1 単体テスト（モックなし・純ロジック）

| 対象 | 確認すること | 対応 AC |

### 10.2 `responses` でモックする範囲

HTTP のやり取り（`ors/client.py` と `generation.py`）。

| テスト | 確認すること |
|---|---|
| 200 の変換 | fixture の JSON から `ProviderRoute` が組めること（距離・ascent・steps・3次元座標） |
| ステータスの翻訳 | 404→`RouteNotFound`、429→`RateLimited`、401→`ApiKeyRejected`、5xx→`ProviderUnavailable` |
| 壊れた JSON | 200 でも `MalformedRoute` になること |
| リトライ回数 | 429 は2回送信され、404 は1回だけであること（`responses` の呼び出し回数で検証） | 
| **打ち切り** | プローブの応答が 300m 超のとき、**2本目以降が1回も登録されないこと**（AC-01-3 / 4.1） |
| 部分的失敗 | 15本中2本が 404 でも 13 本で選択が続くこと（AC-06-4） |
| 全滅 | 15本すべて失敗で `NO_CANDIDATE`（AC-06-3） |
| キー未設定 | 1回も送信せずに `ApiKeyMissing`（AC-06-2） |
| 呼び出し上限 | 1回の実行で消費が15回を超えないこと（7節 API 利用） |

**なぜ「打ち切り」をテストの中心に置くか。** 300m 超の起点で15回消費する
バグは、画面上は正常に見え（結果を拒否するので）、
無料枠の減りとしてしか現れない。実測でしか気づけないバグは
自動テストで止める価値が高い。

### 10.3 fixture

`tests/fixtures/ors_round_trip_5km.json`（既存）を使う。
中身はスパイク1で取得した実レスポンス（暫定座標・points=5・seed=1、
ループ 6177.4m、ascent/descent 67.2m、86 step のうち 82 件が `"-"`、3次元座標）。
自宅座標は含まれていない（確認済み）。

派生ケース（±300m 命中、外れ、異常値 415km、未知の maneuver）は、
**この JSON の距離や type を書き換えた変種**として作る。
**理由:** 新しく API を叩けば無料枠を消費し、実データの形は1件で足りる。
形の正しさは実データで、値の場合分けは変種で確認する。

points=3・`instructions: true` の実データは未取得なので、
最初の実装タスクで1件だけ取得して fixture を追加する（7.3 の要検証）。

### 10.4 モックせず、テストもしないもの

| 対象 | 扱い | 理由 |
|---|---|---|
| ORS の実 API | 叩かない | 遅い・不安定・無料枠を消費（CLAUDE.md） |
| ORS が返す距離の精度 | 検証しない | アプリの責任範囲外（4.1）。スパイクで測った性質を前提とする |
| 並列化の壁時計 | 自動テストで測らない | 実 API なしでは意味のある値が出ない。実測 2.03 秒（FINDINGS スパイク3 C）に依拠する |
| 並列化の**構造** | フェイクのプロバイダでテストする | 同時に投げていること（呼び出しの重なり）はフェイク側で記録できる |
| Streamlit 画面 | 手動確認 | CLAUDE.md の方針 |
| 地図描画 | 手動確認＋HTML に座標が含まれるかの確認 | WORKFLOW.md フェーズ4 のテスト方針 |
| 起点の永続化 | 手動確認（方式決定後） | 方式が未決（8.2）。ブラウザ挙動は自動化の費用対効果が悪い |

### 10.5 実行環境の確認

`uv run pytest` / `uv run ruff check .` / `uv run mypy .` が通ることを
各タスクの完了条件とする（CLAUDE.md）。
