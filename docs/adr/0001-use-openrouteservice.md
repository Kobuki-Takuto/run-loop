# 0001: 周回ルート探索に OpenRouteService を採用する

## ステータス

採用（2026-08-04 決定 / 2026-08-05 に実測で前提を確認）

## 背景

指定した距離に近い周回コース（起点＝終点）を生成する必要がある（US-01）。
自分で経路探索を書かずに済む手段が欲しい。必要な条件は4つ。

1. 周回ルートを距離指定で生成できる
2. 階段を避けられる（AC-03-1）
3. 獲得標高が取れる（AC-03-2 / AC-03-3）
4. 個人利用の頻度で無料枠に収まる（非機能要件）

## 検討した選択肢

| 選択肢 | 評価 | 確認の程度 |
|---|---|---|
| **OpenRouteService（ORS）** | `round_trip` オプションが公式にあり、`avoid_features` と `elevation` を併用できる | **実測で確認**（FINDINGS スパイク1〜4、計 127 呼び出し） |
| GraphHopper | 周回ルートのアルゴリズムがあると聞く。無料枠は ORS より小さいとされる | **未確認。** 呼び出して確かめていない（机上の比較） |
| 自前実装（OSM データ + 探索） | 距離を狙った閉路の探索を自分で書くことになる | 実装せず却下 |

**GraphHopper の評価は未確認である。** 無料枠の大きさも周回機能の使い勝手も
実際に叩いていない。ORS で要件が満たせることを実測で確認した時点で
比較を打ち切った。乗り換えを検討するときは、まずここを測る必要がある。

## 決定

OpenRouteService の `/v2/directions/foot-walking/geojson` を
`options.round_trip`（`length` / `points` / `seed`）で使う。

固定するパラメータ:

| パラメータ | 値 | 理由 |
|---|---|---|
| `profile` | `foot-walking` | 走行を想定。他プロファイルは未検証 |
| `round_trip.points` | 3 | **実測で points が少ないほど精度が良い。** 平均誤差は points=3 で +3.2%（n=5）、5 で +31.1%（n=4）、8 で +57.9%（n=3）（FINDINGS スパイク2）。8 は使わない。2 は未検証 |
| `avoid_features` | `[steps]` | AC-03-1。`round_trip` と併用できることを実測（FINDINGS スパイク1、200 OK） |
| `elevation` | `true` | 獲得標高を同じ応答で得る（ADR-0002） |
| `instructions` | `true` | チェックポイント（AC-04）に steps が必要 |
| `units` | `m` | 距離計算をメートルで統一する |

## 理由

- **周回が公式機能である。** 距離指定の閉路探索を自分で書く工数を丸ごと省ける
- **必要なオプションが併用できることを実測で確認した**（`round_trip` × `avoid_features` × `elevation`、FINDINGS スパイク1）。仕様上可能でも実際に組み合わせが通るかは別問題なので、ここは机上で判断しなかった
- **獲得標高が追加の呼び出しなしで取れる**（ascent / descent = 67.2 / 67.2m の実測。ADR-0002）
- **無料枠が個人利用に足りる。** 2000 回/日（レスポンスヘッダ `X-Ratelimit-Limit` で確認）。1回の実行が15回なので1日 133 回実行できる（requirements 7.1）
- **性能要件を満たせる。** 1呼び出し 1.33〜2.64 秒（n=103）、10本同時の壁時計 2.03 秒（FINDINGS スパイク3 C）。並列化すれば10秒以内（非機能要件）に収まる

## 実測で確認した前提（これが崩れたら再検討する）

| 前提 | 実測値 | 出所 |
|---|---|---|
| 無料枠 | 2000 回/日 | ヘッダ `X-Ratelimit-Limit` |
| 毎分制限 | 直近1分に約40回で 429 | FINDINGS スパイク3 C |
| 404（ルート生成不能） | 自宅 1/103、暫定座標 2/23 | FINDINGS 設計に効いた発見2 |
| 404 は無料枠を消費する | スパイク2 は 23 投で 23 消費（404 2件を含む） | requirements 4.6.1（FINDINGS の初回記述を訂正） |
| 429 は消費しない | スパイク3 は 43 投で 40 消費（429 3件が非消費） | 同上 |
| 起点のスナップは起点座標だけで決まる | 自宅で 0.7m、99 回すべて同一値 | FINDINGS スパイク3 AC-01-3 ＋ 訂正2 |
| 始点と終点は一致する | 0.0m（n=39） | FINDINGS スパイク3 AC-01-3 |

## 結果として受け入れるリスク

| リスク | 実測 | 対処 |
|---|---|---|
| 返却距離が目標から大きくばらつく | 平均比 0.9912、標準偏差 14.5pt（5km で ±725m） | 15本投げて選ぶ（ADR-0003）。**補正係数では解決しない** |
| 場所によって異常系の発生率が違う | 異常ルートは暫定座標 2/23、自宅 0/103 | サニティ上限（目標の3倍超を除外。AC-01-5） |
| 生活道路の名前が取れない | 86 step のうち 82 件（95%）が `"-"` | 名前は稀なボーナスとして扱う（AC-04-4） |
| 接近区間の道と標高が取れない | レスポンスに存在しない | 接近距離という数値だけを表示する（requirements 4.5） |
| サービス停止時に代替がない | 未観測 | `RouteProvider` Protocol で差し替え可能にする（design.md 3節）。代替の実測は未実施 |
| 標高の絶対値に誤差がある | 解像度 約30m | 候補間の相対比較にのみ使う（ADR-0002） |

## 要検証

- GraphHopper の無料枠と周回機能（乗り換え検討時の前提）
- `points=2` の挙動、`foot-walking` 以外のプロファイル
- 目標距離 5km 以外での精度（実測は 5km のみ。requirements 4.7）
- 401/403 や 5xx の実際の応答形（実測での観測はゼロ）
