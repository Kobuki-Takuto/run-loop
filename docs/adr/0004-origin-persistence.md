# 0004: 起点の永続化方式

## ステータス

**採用（2026-08-05）。** ブラウザの localStorage に保存する。
アクセス手段は [`streamlit-js-eval`](https://github.com/aghasemi/streamlit_js_eval)。

保留（同日）から確定に変えた。保留時に「スパイクを1本走らせて決める」としたが、
決め手になったのは走行ではなく**パッケージの保守状況の調査**だったので、
その結果をこの ADR に記録する。

**ブラウザ挙動は依然として未検証である。** 退避条件を「どういう場合に取り消すか」
の節に明記した。未検証のまま採用する理由は「決めるために確かめること」の末尾にある。

## 背景

2回目以降は起点を指定せずに使いたい（US-07）。

- **AC-07-1** 起点を指定すると、その座標がブラウザに保存される
- **AC-07-2** 次回アプリを開いたとき、保存された起点が復元され地図上に表示される
- **AC-07-3** 復元された起点は、地図をクリックすることで上書きできる
- **AC-07-4** 保存された起点がない初回起動時は、起点の指定を促す状態で表示される

**`st.session_state` は使えない。** Streamlit のセッション状態は
ブラウザを閉じると消えるため、AC-07-2 を満たさない（CLAUDE.md の注意点）。
「セッションを超えて復元する」ことが US-07 の要求である。

**requirements.md 4.7 が明示しているとおり、この US には実測の裏付けがない。**
ORS のスパイクは4本走らせたが、ブラウザ側の永続化はスパイク未実施である。

### 保留時から変わった前提

保留時は「起点の座標1つを保存する」問題だった。
**スナップ距離のキャッシュ（design.md 4.6）を同時に決めたことで、
保存項目が4つに増えた。** これが方式の比較を動かしている。

| 保存する項目 | 保留時 | 現在 |
|---|---|---|
| `lat` / `lon` | ○ | ○ |
| `snapped_distance_m` | — | ○ |
| `probed_at` | — | ○ |
| `schema_version` | — | ○ |

## 調査（2026-08-05 実施）

### パッケージの保守状況

判断基準として「最終更新が1年以上前なら URL クエリパラメータ方式に倒す」を
置いて調べた。**結果は割れた。** 本 ADR が保留時に名指ししていた
`streamlit-local-storage` は基準を満たさず、調査中に見つけた
`streamlit-js-eval` は満たす。

| | `streamlit-local-storage` | **`streamlit-js-eval`** |
|---|---|---|
| PyPI 最新 | 0.0.25 / **2024-11-18**（約20か月前） | **1.0.0 / 2026-01-09**（約7か月前） |
| リポジトリ | Socvest/streamlit-local-storage | aghasemi/streamlit_js_eval |
| スター | 16 | **93** |
| 最終 push | 2025-01-02（README のみ）。**コードは 2024-11-18** | **2026-01-13** |
| 未解決 issue | 0（通算5件すべてクローズ） | 1 |
| localStorage | 専用 API（`getItem` / `setItem` / `getAll` / `deleteAll`） | `get_local_storage` / `set_local_storage` / `remove_local_storage` / `clear_local_storage` ＋**任意の JS 評価** |

**`streamlit-local-storage` の未解決 issue が0件なのは、健全さの証拠ではなかった。**
最後の issue #5（2024-12-30）は「`setItem` の直後に `st.rerun()` すると
書き込みが取り消される」という、まさに本アプリが使う経路の欠陥である。
これはコード修正ではなく **README に `time.sleep(1.5)` を足して3日でクローズ**された。
以後コードの変更はない。

### Streamlit 本体の対応

**2026年8月時点でも本体機能は無い。** 最新は 1.61.0。
[native localStorage の要望 issue #5105](https://github.com/streamlit/streamlit/issues/5105)
は 2022-08 に立ち、2026-04-11 更新で **open のまま**、👍 62、
ラベルは `type:possible-component`（本体に入れずコンポーネントで、の意）。
待つ選択肢は無い。

**`st.context.cookies` は読み取り専用である。** 保留時に方式3（Cookie）の
「書き込み手段が課題。読み出しは標準機能でできる見込み（**要確認**）」と書いた点への回答:
読み出しは標準機能で可、**書き込みは不可**。結局コンポーネントが要るので、
方式1と同じ依存追加の話に帰着する。方式3は方式1の劣化版であり、脱落。

### 初回 `None` 問題（保留時の懸念 #2）

**実在する。両パッケージとも文書化している。**

- `streamlit-local-storage` の README: 取得は即座に返らず、
  「アプリが2回描画されるまで値を出さない」
- `streamlit-js-eval`: フロントエンドの応答前は `None` を返す作りで、
  `get_page_href` などが `if location is None: return None` で明示的に処理している

**これは不具合ではなくコンポーネントの通常の挙動である。**
Streamlit のコンポーネントはブラウザと非同期に通信するため、
1回目のスクリプト実行では値が間に合わない。

**設計上の本当の問題は「遅いこと」ではなく「区別がつかないこと」だった。**
`localStorage.getItem()` はキーが無いときも `null`（Python では `None`）を返す。
つまり「まだ読めていない」と「保存が無い」が同じ値になる。
`None` を「保存が無い」と解釈すると、毎回の起動で AC-07-4 の画面が一瞬出てから
復元に切り替わり、AC-07-2 と AC-07-4 が画面上で混ざる。

対処は design.md 8.4 に置いた。要点は2つ。

1. **`load()` は3状態（`PENDING` / `EMPTY` / `LOADED`）を返す。** `None` を返さない
2. 区別のために生のキーを読まず、**必ず値が返る式**を評価する
   （`JSON.stringify({v: localStorage.getItem(...)})`）

`time.sleep()` で待つ対処は採らない。待ち時間は環境で変わり、
待てば十分という保証がどこにもない。

**この2点目が `streamlit-js-eval` を選ぶ決め手になった。**
`get_local_storage` のような localStorage 専用ヘルパは、
「未読」と「保存なし」をどちらも `None` で返して区別できない。
汎用の JS 評価に降りられるパッケージであれば、判別を自前で作れる。
`streamlit-local-storage` にはこの逃げ道が無い。

### 未解決の懸念: Community Cloud の iframe

[ある技術記事](https://dev.to/hendrixaidev/how-i-solved-streamlit-session-persistence-after-3-failed-attempts-b4c)（2026-02）が
「Streamlit Cloud ではコンポーネントの iframe が隔離され、
localStorage はその iframe 固有の領域に入るのでリロードで消える」と主張し、
`streamlit_js_eval`・`extra-streamlit-components` の Cookie・
`window.parent.localStorage` の3方式が失敗したとして `st.query_params` に移行している。

**この主張は採らないが、否定もできない。**

- 出典はこの記事1本のみ。査読も再現手順もない
- 記述の内容が、上に書いた初回 `None` 問題との混同を強く疑わせる
  （「保存したのにリロードで消えた」は、未読状態を「保存なし」と解釈した場合の症状と同じ）
- Streamlit はコンポーネントの静的ファイルをアプリと同一オリジンから配信するため、
  理屈のうえでは iframe と親ページの localStorage は共有される
- もし本当に全面的に壊れているなら、両パッケージにその報告が積まれているはずだが、
  未解決 issue は 0 件と 1 件である

**ただし Community Cloud は本アプリの公開先である**（WORKFLOW.md フェーズ7）。
確認せずに済ませられないので、design.md 11節 #3 として残し、
下の退避条件に結び付けた。

## 決定

**ブラウザの localStorage に保存する。アクセス手段は `streamlit-js-eval`。**

### 却下した方式

| 方式 | 却下の理由 |
|---|---|
| **URL クエリパラメータ**（`st.query_params`） | 追加依存ゼロだが、**自宅座標が URL に載る**。履歴・共有・スクリーンショットで漏れる。保存項目が4つに増えたことで、座標に加えて**プローブ日時**（＝その座標に居た日時）まで載ることになり、保留時より不利になった |
| **Cookie** | 書き込みにコンポーネントが必要（`st.context.cookies` は読み取り専用）。依存追加の話に帰着するので方式1の劣化版 |
| **サーバ側のファイル** | AC-07-1 が「ブラウザに保存」と定めている。加えて Community Cloud はコンテナ再起動でファイルが消えるため、そもそも永続しない |
| **`streamlit-local-storage`** | 判断基準（1年以内の更新）を満たさない。加えて、本アプリが使う経路の既知欠陥が `time.sleep(1.5)` という回避策で閉じられている。汎用 JS への逃げ道もない |

**URL クエリパラメータは「却下」ではなく「退避先」でもある。** 下記のとおり。

### 新しい依存の追加について

`streamlit-js-eval` 1件を追加する（CLAUDE.md により事前に確認済み）。

- 依存は `streamlit>=1.0.0` のみで、推移的な依存を持ち込まない
- localStorage 専用ではなく汎用の JS 評価なので、
  ヘルパが足りなくても任意の JS に降りられる（初回 `None` の判別で実際にそうする）
- 追加は `uv add streamlit-js-eval`（`pip` は使わない）

## 保存する内容とその扱い

詳細は design.md 8.2 / 8.5 / 8.6。ここでは決定の要点だけ記す。

**保存項目は4つ。** `schema_version` / `lat` / `lon` / `snapped_distance_m` / `probed_at`
を localStorage のキー1つに JSON 1件として入れる。保存するのは1件のみ
（複数起点はスコープ外。requirements 3.2）。

**接近ゲートを通った起点だけを保存する。** REJECT された地点は起点として確定しない。
結果として「保存された値が読めた ⇒ その起点は OK か WARN」が不変則になり、
`snapped_distance_m > 300` は**それ自体が破損の証拠**として使える。

**無効化の条件は5つ。** 起点の変更（上書き）、`schema_version` の不一致、
`probed_at` から30日、実測との乖離検出、値の破損。
**このうち「実測との乖離」が最も重要である。**
「スナップ距離は起点だけで決まる」は ORS の実測事実であってドメインの不変則ではない
（design.md 2.2 と同じ理由）。キャッシュはこの事実を構造の前提に格上げする操作なので、
前提が崩れたことに気づく手段を同時に持つ。持たなければ、崩れたとき静かに間違える。

**壊れていたら黙って捨て、初回起動と同じ状態にする。画面にエラーを出さない。**
ユーザーに取れる行動が「地図をクリックする」しかなく、初回起動の案内と同一だからである。
**ただしログには出す**（座標は出さない。壊れ方の分類だけ）。
座標が妥当でスナップ距離だけ壊れている場合は、**起点だけ救う。**

## スナップ距離を一緒に保存する判断

この ADR で同時に決めた。design.md 4.6 に設計を置いた。

**成立する。** 根拠と、それに付けた条件を記す。

| 論点 | 判断 |
|---|---|
| 速度 | 2回目以降は 約4〜5秒 → **約2秒**。1回目は従来どおり二段投入 |
| 呼び出し数 | 実行あたりの directions は**どちらの経路でも15回**。上限（要件7節）は不変 |
| 追加費用 | 起点1つにつきプローブ1回。無料枠 2000回/日に対して無視できる |
| 打ち切り | **強くなる。** 不適切な起点は確定時に弾かれ、directions は0回 |
| 早期警告 | 目標距離の入力前に警告できる。AC-01-3 の文言をそのまま前倒しできる |

### 前提を増やさないための2つの選択

**1. プローブは `/v2/snap` で投げる。directions を1本捨てるのではない。**

directions を使うと、目標距離が未入力なので仮の length を作る必要があり、
**「スナップ先は length に依存しない」という未実測の仮定**が新たに要る。
n=99 が確かめたのはシード非依存であって、目標距離の非依存ではない。
`/v2/snap` には length の概念が無いので、この仮定が消える。
加えて `snapped_distance` が直接返り、半径内に道路が無ければ `null` が返る。

**前提を増やさずに済む方を採る。** 代わりに
「`/v2/snap` のスナップ先が directions と一致するか」が新たな要検証になったが
（design.md 11節 #12）、これは乖離検査が事後に捕まえる範囲にある。

**2. `Candidate.approach_m` は候補ごとの実測のままにする。**

キャッシュ値は**接近ゲートの入力にしか使わない。** 表示と ±300m 判定は
これまでどおり各応答の `snapped_start` から算出する（design.md 2.2 を変えない）。
キャッシュ値を表示や判定に流用すると比較対象が消え、乖離検査そのものが書けなくなる。

### 受け入れたリスク

**プローブは地図のクリックごとではなく、起点の確定操作で投げる。**
AC-05-1 は「玄関を正確に」なので、ユーザーはピンを何度も微調整する。
クリックごとに投げると1クリック1回の消費になる。確定を挟めば起点1つにつき1回で済む。
確定は目標距離の入力より前なので、早期警告の利益は保たれる。

**キャッシュが誤っていれば、悪い起点に15回使う。**
経路 A はキャッシュを信じてゲートを飛ばすためである。
損害は1回の実行に限られ、以後は乖離検査でキャッシュが破棄されて経路 B に落ちる。
**この1回ぶんの露出は受け入れる。** 事前に防ぐにはゲートを毎回投げることになり、
キャッシュの目的そのものが消える。

## どういう場合にこの決定を取り消すか

**次のいずれかが起きたら、URL クエリパラメータ方式に切り替える。**

1. Community Cloud で、ブラウザを閉じて開き直したときに値が復元されない
2. iOS Safari（ホーム画面に追加した状態）で、翌日に値が残っていない
3. design.md 8.4 の3状態の判別が成立しない（`PENDING` と `EMPTY` を分けられない）

切り替えたときに変わるのは `persistence.py` の実装1つと依存の削除だけである
（`ui/app.py` は `OriginStore` にしか触らない。design.md 8.3）。
**ただし切り替えると自宅座標とプローブ日時が URL に載る。**
そのときは保存項目を絞る（`probed_at` を捨ててスナップ距離のキャッシュを諦める）
判断も同時に要る。

**この退避が要るかどうかは、公開後の最初の確認で分かる**（WORKFLOW.md フェーズ7）。

## 決めるために確かめること（未実施）

方式は決めたが、ブラウザ挙動は依然としてスパイク未実施である。

| # | 確認すること | design.md 11節 |
|---|---|---|
| 1 | アプリを開き直したときに保存値が復元されるか（Community Cloud 上で） | #3 |
| 2 | 初回描画で 8.4 の判別式が `PENDING` と `EMPTY` を分けるか | #3 |
| 3 | iPhone の Safari で、ホーム画面に追加した状態で保持されるか | #3 |
| 4 | プライベートブラウズやサイトデータ削除で消えたときの挙動 | #3 |
| 5 | `/v2/snap` のスナップ先が directions と一致するか | #12 |
| 6 | `/v2/snap` が directions と同じ無料枠を消費するか | #13 |

**#1〜#4 は ORS の無料枠を消費しない。** #5・#6 は数回消費する。

**未検証のまま採用する理由。** #1〜#4 はローカルでは確かめられない
（Community Cloud と iOS が要る）ので、デプロイ（WORKFLOW.md フェーズ7）まで
どのみち答えが出ない。それまで保留を続けると US-07 が着手できず、
`persistence.py` の実装が空のまま最後まで残る。
方式を決めて実装し、フェーズ7で判定して必要なら退避する方が、
確認できる時期が早く、退避の費用も小さい（`persistence.py` の1実装）。

US-07 は引き続き実装タスクの最後に回す（他の US はこれに依存しない）。

## どの方式でも守ること

- **座標を URL・ログ・エラーメッセージに出さない。** 保存対象は自宅である
- **`probed_at` も同じ扱いにする。** 「その座標に居た日時」を意味しうる
- **座標を丸めない。** AC-05-1 は「自宅の玄関を正確に起点にしたい」であり、
  プライバシーのための丸めは要件と衝突する。保存場所を選ぶ側で守る
- 保存する起点は1件のみ（複数の起点の登録はスコープ外。requirements 3.2）
