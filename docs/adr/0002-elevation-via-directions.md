# 0002: 獲得標高を directions の `elevation=true` で取得する

## ステータス

採用（2026-08-05、FINDINGS スパイク1 の実測に基づく）

## 背景

坂の少ないコースを優先して選ぶ必要がある（US-03 / AC-03-2）。
選択の第2基準が獲得標高なので、**候補15本すべてに標高が必要**である。
1本だけ取れれば済む話ではない。

## 検討した選択肢

| 選択肢 | 追加の呼び出し | 評価 |
|---|---|---|
| **directions に `elevation: true` を付ける** | **0回** | ルート本体の応答に `ascent` / `descent` が含まれる |
| ORS の Elevation API を別に呼ぶ | 候補1本につき1回（15本で +15回） | 呼び出しが倍になる |
| 標高を使わず距離だけで選ぶ | 0回 | AC-03-2 を満たせない |

## 決定

directions の呼び出しに `elevation: true` を付け、
レスポンスの `properties.ascent` を候補の獲得標高として使う。
別の標高 API は呼ばない。

## 理由

- **追加の API 呼び出しがゼロである。** 実測で `round_trip` と `elevation: true` が
  併用でき、`ascent` / `descent` が返ることを確認した
  （67.2 / 67.2m。周回なので一致する。FINDINGS スパイク1）
- **呼び出し回数の予算に直接効く。** 標高を別に取ると1回の実行が 15 → 30 回になる。
  毎分制限は約40回（FINDINGS スパイク3 C）なので、
  **30回では1分に1回しか実行できなくなる。** 15回なら2回実行しても 30 回で収まる
  （requirements 7.1）。無料枠 2000 回/日に対しても1日 66 回に半減する
- **精度は足りている。** ORS の標高は解像度 約30m 程度で絶対値に誤差があるが、
  AC-03-2 が要求するのは**候補間の相対比較だけ**である
  （FINDINGS 設計に効いた発見7）

## 結果として受け入れること

- **座標が3次元になる。** `elevation: true` では geometry の各点が
  `[lon, lat, ele]` で返る（実測で確認、295 点すべて3要素）。
  地図描画と haversine は先頭2要素のみ使う。
  3要素目を無視する処理を `ors/mapper.py` に閉じる（design.md 1.2）
- **獲得標高はループ区間のみの値である。** 接近区間の標高はレスポンスに存在せず、
  加算できない（requirements 4.5）。したがって画面には
  「ループ区間のみ」の注記を必ず添える（AC-03-3）。
  注記なしで出すと、接近距離が大きい起点で実態と合わない値になる
- **絶対値としては表示するが、判断は相対比較に限る。** 「67m」という数字を
  出すこと自体は AC-03-3 の要求だが、他のアプリの数値と比べられるほどの
  精度はない

## 却下した選択肢の理由

**Elevation API を別に呼ぶ。** 精度が上がる保証がないのに（同じ標高データ源）、
呼び出し回数が倍になり毎分制限に接触する。相対比較しか要求されていないので
払う価値がない。

**標高を使わない。** AC-03-2 が「距離条件を満たす候補が2件以上ある場合、
獲得標高が最小の候補が選ばれる」と定めている。実測では 15本で
±300m を満たす候補が平均 5.0 本得られる（FINDINGS スパイク4）ので、
この分岐は通常発生する。使わない選択は要件違反になる。

## 要検証

- `descent` と `ascent` が周回で常に一致するか（実測は1本のみ）。
  一致しない場合、どちらを使うかは AC-03-2 の「上り累計」に従って `ascent`
- 標高データの解像度が坂の判別に足りるか（走ってみて実感と合うか）
