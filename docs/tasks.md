状態: 完了

### 目的

要件由来の数値を1か所に集め、設定の欠落で**静かに間違えない**ようにする。

### 触るファイル

`runloop/config.py`, `tests/test_config.py`

### 依存

T03

### 完了条件

- [x] 定数（±300m / 15本 / 50m・300m / TTL 30日 / 乖離 10m / タイムアウト 8秒 / 送信上限 18回）が `config.py` にあり、コード中に散っていない
- [x] AC-06-2「API キーが未設定の場合、設定が必要である旨のメッセージが表示される」→ キー欠落時に**1回も送信せず** `ApiKeyMissing`
- [x] `os.getenv(...) or <定数>` および `.get(key, <それらしい既定値>)` の形が `runloop/` に無い（design.md 3.3。`spike/` のフォールバック座標を本体に持ち込まない）
- [x] 起点を環境変数から読まない（起点はブラウザの永続化のみ。design.md 3.3 の表）
- [x] 欠落時のメッセージにキー名と探した場所が入り、値そのものはログにも画面にも出ない
- [x] テストを先に書き、失敗を確認してから実装した

### 実装メモ

- **読み出し元を `load_settings(env)` の引数で受ける形にした**（2026-08-06 承認）。
  design.md 3.3 はキーの出所を「`.env` / `st.secrets`」としているが、`runloop/` は
  Streamlit を import できない（design.md 1.2）ため受け渡し方が未定だった。
  `ui/` が `st.secrets` を渡し、引数を省いたときだけ `.env` と `os.environ` を見る。
  **design.md 3.3 に判断を追記した**（`ui/` が `os.environ` へ書き写す案を採らない理由つき）
- 閾値4件は `models.py` から import し、**構文木で「代入していない」ことを固定した。**
  値の一致だけを見るテストは、同じ数値を書き写しても通ってしまう（T02 の申し送り）
- **「定数が散っていない」の検査を構文木（AST）で行った。** ソースの文字列検索では
  docstring の「15本投げる」のような説明文に反応する（実際 `ports.py` にこの記述がある）。
  `ast.Constant` の数値だけを見れば説明文と区別できる。値だけでなく型も比較している
  （`10` と `10.0` は `==` で等しいため、無関係な整数を乖離の許容値と誤認しないように）
- `.get(key, <既定値>)` を禁止しているので、`config.py` 自身も `in` で有無を見てから
  `[]` で読む。**禁止の対象に自分を含めた**（テストは `runloop/**` 全体を走査する）
- `Settings.api_key` は `repr=False`。データクラスの既定の `repr` は全項目を出すため、
  この型が例外メッセージやログに混ざるとキーが漏れる。型の側で隠す
- 空白だけのキーを欠落として扱う（`.env` に `ORS_API_KEY=` と書いただけの状態）。
  通すと送信して 401 になり、AC-06-2 の「設定が必要」を伝えられない
- 値だけでなく**関係も2件固定した。** `MAX_SEND_ATTEMPTS > CANDIDATE_COUNT`（逆転すると
  1回のリトライで上限を破る）と `SNAP_RADIUS_M > APPROACH_REJECT_M`（半径を 300 に
  合わせると拒否すべき起点が「道路なし」の変種に落ち、AC-01-3 の文言を距離つきで出せない）
- **非機能要件「毎分40回未満」は定数にしていない**（2026-08-06 承認）。使う側
  （T08 以降）がまだ無く、T19 の確認項目のため、使う場所ができた時点で足す
- 実装後、故意に壊した10パターン（閾値の再定義・`.strip()` の除去・メッセージから
  キー名を落とす・`repr=False` の除去・既定キーへのフォールバック・`Settings` に
  起点を足す・`HOME_LAT` を読む・`ports.py` に 350 を書く・送信上限を15に・
  半径を300に）で、意図したテストが落ちることを確認した

### 触るファイル

### 依存

### 完了条件

      → `ors_round_trip_5km_points3.json`（258 座標・71 step・47KB）

      → **消費する（1回あたり1）。** ただし「directions と同じ枠か」は未確定。

      （依存は spike → runloop の向きのみ）

### 実装メモ

- **送信5回・消費4回だった**（予定は「約3回」）。超えた理由は2つ。
  **(a) snap に `/geojson` を付けて 406 になった**（`code: 8007`。**枠は消費していない**）。
  directions が `/geojson` を取るので同じ形だと思い込んだのが誤り。
  **(b) 残数ヘッダの解釈が1回では確定せず snap を2回投げた**（tasks.md が
  snap を「1〜2回」と見込んでいた範囲内）
- **`/v2/snap` は GeoJSON を返せない。** 素の `/v2/snap/{profile}` に
  `Accept: application/json` で投げ、`locations[0]` を読む（圏外は `null`）。
  T07 の実装に直接効くので design.md 4.6.1 と 11節 #15 に書いた
- **type 13 が5件実測された。** design.md 7.1 が「未観測」としていた種別で、

## T09: generation.py — 一括並列（経路A）と乖離検出

状態: 完了

### 目的

スナップ距離のキャッシュが有効なとき、接近ゲートを判定済みとして15本を一括で投げる
（節約するのは呼び出し数ではなく**時間**）。同時に、キャッシュが誤っていたことに
気づく手段を持つ。

### 触るファイル

`runloop/generation.py`, `tests/test_generation.py`

### 依存

T08

### 完了条件

- [x] キャッシュが有効なとき、プローブを挟まず15本が同時に登録される（design.md 10.2「一括並列」／4.6.2 経路A）
- [x] キャッシュがない／失効しているときは二段投入（経路B）に落ちる（同「経路の切り替え」）
- [x] どちらの経路でも directions は15回（非機能要件「15 回以内」）
- [x] 各候補の `approach_m` がキャッシュ値と **10m を超えて**離れていたら、キャッシュ破棄を呼び出し側に通知する（design.md 8.5.1）
- [x] AC-01-2 の判定と表示には**各応答の `snapped_start` から算出した値**を使い、キャッシュ値を流用しない（design.md 2.2 / 8.5.1）
- [x] 乖離を検出したらログに出す（座標は出さない）
- [x] テストを先に書き、失敗を確認してから実装した

### 実装メモ

- **キャッシュは `cached_approach_m: float | None` で受ける**（2026-08-06 承認）。
  失効（30日）・不変則違反・壊れた値の判定は T14 の `persistence.py` の責務なので、
  **`generation.py` は現在時刻を知らない。** `OriginRecord` ごと渡す案を採ると
  同じ失効規則が2か所に分かれ、片方だけ直したときに静かに食い違う。
  `None` は「キャッシュなし・失効・破棄後」をまとめて表し、経路Bに落ちる
- **`GenerationOutcome.cache_diverged` は通知であって破棄ではない。** 破棄するのは
  呼び出し側で、生成側は保存先を知らない（design.md 8.3 のポート）。
  キャッシュを使わなかった実行と、1本も測れなかった実行では `False`——
  比べる相手が無いことと「ずれていた」を区別する（T08 の `approach_m=None` と同じ判断）
- **経路A でも `verdict` と `approach_m` は各応答の実測から出す**（2026-08-06 承認、
  design.md 4.6.3 に追記）。design.md は「キャッシュが誤っていれば15回使う」ことを
  受け入れると書いていたが、**その実行の結果を表示するかを決めていなかった。**
  キャッシュ値（20m = OK）を verdict に流すと、実測 420m の起点のコースが画面に出て
  AC-01-3 を破る。キャッシュは**ゲートを飛ばす判断**にだけ使い、**結論**は実測から出す
- **キャッシュ値が 300m 超だった場合の防御を足していない**（2026-08-06 承認）。
  design.md 8.2 の不変則（ゲートを通った起点だけ保存する）と T14 の完了条件
  （`snapped_distance_m > 300` は破棄）で二重に防がれている。テストの根拠がない
  防御を足さない方針（T02 / T03 / T06 / T07 / T08 と同じ）
- **「プローブを挟まない」は本数では主張できない**（どちらの経路でも15本）。
  **15人ぶりのバリア**で待ち合わせ、1本目を待つ実装なら全員がそろわず時間切れに
  なる形で固定した（T08 の14人ぶりのバリアと同じ手口。壁時計は測らない）
- **乖離の境界（ちょうど 10.0m）は実測値から差を引いて作った。** 座標から算出した
  接近距離では厳密な等号を作れない（T08 が 50.0 / 300.0 で断念した点）が、
  **キャッシュ値の側を `実測 - 10.0` で作れば**差はちょうど 10.0 になる。
  引き算が誤差なく 10.0 を返すことはテスト自身が先に検査する（前提が崩れたら
  「境界を検査したつもり」で通り続けるより落ちるほうがよい）
- **穴が1件見つかり、テストを足した。** 経路Aの `calls_consumed` を
  `len(candidates)` で数える破壊が最初は通った（部分的失敗のテストが消費回数を
  見ていなかった）。失敗した2本も枠を消費しているので、**失敗のある実行ほど
  消費を少なく見積もる**バグになる。等号の検査を足した
- 実装後、故意に壊した21パターン（プローブを挟む・キャッシュ無しでも一括・並列度を
  1に・プローブを別枠で16回・消費を候補数で数える・verdict をキャッシュから・
  approach_m をキャッシュから・候補の接近距離をキャッシュで埋める・乖離を検査
  しない・常に乖離・先頭だけ比べる・プローブを比較から外す・平均で比べる・
  測れないとき乖離扱い・乖離で候補を捨てる・ログを出さない・ログに座標・許容を
  100m に・境界を「以上」に・snap を投げる・シードを固定）で、**21件すべて**
  意図したテストが落ちることを確認した
